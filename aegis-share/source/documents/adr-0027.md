# 0027. The SessionStart marker clear keys on session identity, not on the event firing

- Status: accepted
- Date: 2026-08-04

## Context

ADR-0013 gave `session-start-env-check.sh` one job beyond reporting degrades:
clear every per-session gate marker, so one session's state cannot authorise
another's commit. It cleared unconditionally, on every `SessionStart`.

That holds while `SessionStart` means "a new session began". In this project's
remote containers it does not. The event also fires when an MCP server
reconnects, and reconnects happen repeatedly inside one continuous session.

On 2026-08-03/04 that cost three complete find→verify passes on one change.
Each pass ran to completion, each wrote `.review-stamp`, and each stamp was gone
before the commit it authorised could run — every loss landing on a turn
boundary, never inside a turn. The diagnosis is by elimination plus one positive
signal: `session-start-env-check.sh` is the only thing in the repository that
removes `.review-stamp` without a commit (`post-bash-stamp-consume.sh` needs a
commit that leaves the tree clean, and no commit ran), and it is likewise the
only remover of `.aegis-unavailable`, which was observed vanishing in the same
instant as a stamp.

The failure mode is the one ADR-0013 exists to prevent, inverted. A gate that
cannot be *earned* is as broken as one that cannot be trusted: three passes, ~300k
tokens, and no commit.

## Decision

Clear the markers only when the session actually changed. The hook reads
`session_id` from the `SessionStart` payload and compares it with the value
remembered in a new `.claude/.session-id` marker:

- **Different, or nothing remembered** — a genuinely new session. Clear all six
  markers, then record the new id.
- **Equal** — the same session re-firing. Keep everything.
- **`session_id` absent, unreadable, or no `jq`** — clear unconditionally and
  drop the remembered id. This is exactly the behaviour the hook had before, so
  a payload shape this repository has not captured cannot make the gate more
  permissive than it already was.

`.session-id` is deliberately excluded from the list it guards: it is the memory
the comparison reads, and clearing it would make every `SessionStart` look new.
It is added to `.gitignore` in the same change — per ADR-0022, an un-ignored
marker enters the working-tree hash, so writing it would move the value the
pairing is about to compare against and no pass could ever stamp.

`session_id` is read from the payload rather than trusted from documentation,
and `scripts/test-review-gate.py` drives the real hook across both branches:
an unseen id clears and records, the same id keeps, a different id clears and
re-records, an absent id clears and forgets. One case fires a `SessionStart`
*mid-cycle* — between the finder finishing and the verifier being dispatched,
the only point at which "keeps them as one block" is observable, because the
verifier's stop consumes the pairing markers — and asserts the pass still stamps.

## Alternatives considered

- **Filter on the payload's `source` field** (`startup` / `resume` / …): rejected
  for now. It may well be the better key, but no real payload has been captured
  here, and choosing a discriminator whose values are unknown would repeat the
  fault ADR-0022 records — describing hook behaviour from documentation rather
  than from an observed payload.
- **Stop clearing review markers at `SessionStart` and rely on the pairing hash
  alone**: rejected. The pairing proves the parent did not edit between the two
  agents; it says nothing about how much later the stamp is spent. Removing the
  clear entirely widens the same hole further than this does.
- **Revert and accept the cost**: rejected after weighing it. The cost is not a
  slow gate, it is a gate that could not be passed at all in this environment.

## Consequences

- A stamp now survives a reconnect-driven `SessionStart`, which is the whole
  point. The fix was confirmed live: the first `SessionStart` after it landed
  reported `gate markers kept`.
- **Accepted residual risk, in the unsafe direction.** `pre-bash-guard.sh`
  authorises a commit on `.review-stamp` merely existing, and ADR-0019 already
  stopped edits from clearing it, so this clear was the last backstop against a
  stamp earned in one context authorising a commit in an unrelated one. It was
  unconditional; now `session_id` equality is the only discriminator. Two ways
  that loses: an id reused after the tree changed out of band (`/resume`, a
  restored container snapshot), and two concurrent sessions sharing one
  `.claude/` directory, where the second to fire reads the first's id. Neither is
  checkable from inside this repository — the payload's uniqueness and lifetime
  are the platform's to guarantee. Before leaning on this mechanism further,
  settle it against the `SessionStart` payload documentation.
- **A third case, failing safe.** The clear and the record are two filesystem
  steps, not one. A hook killed between them leaves the id unwritten, so the next
  same-session fire clears again for nothing — the old cost, once. Reordering
  would invert it rather than fix it: recording first lets an interrupted run
  skip a clear it owed, which is the unsafe direction. A temp-file-and-rename
  makes the write atomic but does not join it to the clear, so the race narrows
  and does not close. Left as is deliberately.
- The hook is no longer a straight-line `rm -f`. Its degraded path is now the
  thing to keep honest: if the fail-safe branch ever stops clearing, the gate
  silently weakens instead of loudly blocking, which is the failure direction
  ADR-0013 cares about. That is what the absent-id test case pins.
