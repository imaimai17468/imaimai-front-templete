# 0028. The marker clear also keys on `source`, which `/clear` made necessary

- Status: accepted
- Date: 2026-08-04

## Context

ADR-0027 made `session-start-env-check.sh` clear the gate markers only when
`session_id` changed. It considered keying on the payload's `source` field and
rejected it *for now*, on the grounds that the field's values were unknown and
choosing a discriminator from documentation rather than an observed payload is
the fault ADR-0022 records. It closed by naming the follow-up: settle it against
the `SessionStart` payload documentation before leaning on the mechanism further.

That search has now been done. `source` carries one of five documented values —
`startup`, `resume`, `clear`, `compact`, `fork`. Two consequences fall out, and
the second is the reason this ADR exists rather than a note on the first.

**The resume risk ADR-0027 accepted looked addressable, and is not.** It named id
reuse after an out-of-band change (`/resume`, a restored snapshot) as an unsafe-
direction risk it could not check, and `resume` is one of the five values, so the
first draft of this decision forced a clear on it. That draft cost a stamp within
minutes of landing. `resume` is observed firing inside continuous work in this
environment — one logged instance carried an id that matched the remembered one —
and that single occurrence was enough: treating it as a task boundary reinstates
the treadmill ADR-0027 exists to stop. How often it recurs is unmeasured and does
not need to be. The value being available did not make it the right discriminator.

**ADR-0027 opened a hole nobody caught, including its own review.** `/clear`
resets the conversation — a different body of work starts. Five review passes
over that change never asked what happens if `session_id` survives `/clear`: the
markers would be kept, and an unreviewed task could spend the previous task's
stamp. That is precisely the exposure ADR-0019's stamp-consume rule exists to
police, reopened from a new direction. Whether `session_id` actually persists
across `/clear` is *not* documented — so this is an unbounded risk, not a
demonstrated bug, and it is cheaper to close than to establish.

## Decision

`source` becomes an **additional** clear-trigger, not a replacement. The markers
are kept only when the id matches **and** `source` is not `clear` or `fork` — the
two that begin a different body of work whatever the id says. `resume` is
excluded for the measured reason above; `compact` and `startup` never forced a
clear.

Replacement was rejected deliberately. Which `source` an MCP reconnect reports is
still unobserved; if it reports `startup`, keying on `source` alone would undo
ADR-0027 entirely and restore the bug that cost three passes. Adding a trigger
cannot do that — the change is strictly in the safe direction.

The fail-safe rule from ADR-0027 extends unchanged: an absent or unrecognised
`source` is never a reason to keep. Only the two listed values force a clear;
everything else falls through to the id check, which itself falls through to an
unconditional clear when the id is missing. `scripts/test-review-gate.py` pins
all of it against the real hook — each of the two forcing a clear on the
keep-branch's exact precondition (same id, stamp earned), `compact` and `startup`
keeping, and an unknown value falling back to the id check rather than to "keep".

## Alternatives considered

- **Replace the id check with `source`**: rejected, above. It is the more elegant
  key and may become the right one, but only after somebody observes what a
  reconnect reports.
- **Leave it and record the `/clear` hole as accepted risk**: rejected. ADR-0027
  already carries two accepted unsafe-direction risks; adding a third that is
  cheap to close would be using the residual-risk section as a place to put
  things rather than a place to declare them.
- **Establish first whether `session_id` survives `/clear`, then decide**:
  rejected as sequencing. The observation is worth having, but the fix does not
  depend on its outcome — forcing a clear on `clear` is correct either way, and
  waiting leaves the hole open meanwhile.

## Consequences

- Amends ADR-0027, whose Decision now reads as the id half of a two-part rule.
  Its accepted-risk list is unchanged — the `resume` entry survives, for the
  reason in Context — and gains nothing. What it loses is the `/clear` exposure
  it opened without noticing.
- **A stamp does not survive `/clear`** — provided the harness reports
  `source: clear` for it, which is documented and unobserved, exactly as the last
  bullet says of every value here. If a `/clear` lands mid-task with work still to
  commit, the next commit needs a fresh review. That is the intended cost and the
  right side to err on.
- The keep-branch's precondition is now two facts instead of one, so the test
  suite has to state which one each case is exercising. Every new case therefore
  sets both fields explicitly rather than relying on a default.
- **`source`'s values are documentation, not an observed payload** — the standard
  ADR-0027 held itself to and could not meet. The mitigation is that an
  unrecognised value cannot make the gate more permissive, so the cost of the
  documentation being wrong is bounded at "clears more often than needed".
