# 0029. Review and spec verification each run as one agent with internal stages

- Status: accepted
- Date: 2026-08-07

## Context

ADR-0015 made both pipelines flat finder → verifier pairs of depth-1 agents:
`code-reviewer` → `review-verifier` for the pre-commit review, `spec-verifier` →
`spec-checker` for design-time spec checking. Its load-bearing property was
find ≠ verify independence — a fresh, finding-blind context refutes — which
across this project's review history killed roughly a quarter of all candidates.

The expensive part was never the second agent. It was what a *gate* must prove
once there are two dispatches: that the parent did not edit the tree between
them. That single invariant is why `.finder-done`, `.finder-hash`, `.pair-ok`,
`pre-agent-review-pair.sh` and `lib-review-hash.sh` exist, and the record of what
it cost is unusually complete:

- ADR-0022 — the wrong event first (`PostToolUse`, which fires at launch), then
  two wrong sampling windows (each containing one agent's own run, so the agents'
  scratch files voided innocent passes), plus a hook shipped without its
  executable bit. Four review cycles, three of which could not stamp.
- ADR-0027, then ADR-0028 — once four markers had to survive across a session
  boundary but not across a task boundary, *when to clear them* became its own
  decision, revised twice within one day. Both exist to police a marker set that
  three of four entries only ever served the pairing check.
- `review-diff` step 0 — a paragraph of unresolved observation about
  `run_in_background`, most of which is about a **pair** of dispatches arriving as
  two turns rather than one block.

The repository owner asked for one agent per pipeline, with the stages kept
inside it, and for a simpler stamp. The shape is taken from a fork of this
template that made the same change on 2026-08-07 and could not discharge its
evaluation obligation; see the last consequence.

## Decision

**One agent per pipeline, stages internal.**

- Review: `code-reviewer` alone (`model: sonnet`). Stage A find across all
  lenses, coverage-first → B dedup by (file, line) → C refute each candidate by
  re-deriving it from the real code → D return survivors with `fix` and
  `acceptance`. ADR-0020's contract is unchanged; ADR-0019's single pass is
  unchanged.
- Spec: `spec-verifier` alone (`model: opus`). Stage A formalize → B hunt →
  C replay each candidate against the machine → D return survivors. Still
  design-time, still no gate, still no auto re-run.
- `review-verifier` and `spec-checker` are deleted.

**The names stay.** ADR-0013, ADR-0015, ADR-0019 and ADR-0022 all name
`code-reviewer`; `pre-agent-review-clear.sh` filters on
`subagent_type == "code-reviewer"` and `.claude/settings.json` matches the same
string. Renaming would point four records at an agent that does not exist — the
reason ADR-0022 kept its own hook filename.

**Stage C cites what it read.** Each verdict carries the `file:line` the stage
re-derived it from, so a refutation that never opened the code is visible in the
output. This is a disclosure, not a guarantee (see Consequences).

**The stamp needs one fact: the review agent finished having reported
something.** `SubagentStop` for `code-reviewer`, plus ADR-0022's non-blank
`last_assistant_message` check — which was one of three facts and is now the
only one, so it carries the whole gate. Deleted with the second dispatch:
`.finder-done`, `.finder-hash`, `.pair-ok`, `pre-agent-review-pair.sh`,
`lib-review-hash.sh`, and one `SubagentStop` matcher. `pre-agent-review-clear.sh`
(stamp cleared at cycle start) and `post-bash-stamp-consume.sh` (ADR-0019's
clean-tree consumption) are untouched.

**ADR-0027 and ADR-0028 survive, applied to one marker.** Their decision — keep
the gate's state only when `session_id` matches *and* `source` is neither `clear`
nor `fork` — is about session boundaries, not about how many markers exist. The
rule is unchanged and its reasoning is untouched; the set it governs drops from
four files to `.review-stamp` alone.

**The stamp hook treats `finder`, `verifier` and no argument alike.** Whether the
harness re-reads `.claude/settings.json` mid-session is not established here, so a
cached registration still passing `verifier` must stamp rather than wedge every
commit. `scripts/test-review-gate.py` pins all three invocations.

## Alternatives considered

- **Keep both two-agent pipelines**: rejected by the repository owner, who asked
  for the merge after the independence trade-off was stated.
- **Merge review only, keep the spec pipeline two-staged**: rejected. It leaves
  one discipline with two shapes for no stated reason.
- **Keep two agents but drop the pairing check**: rejected — it pays the cost of
  two dispatches and gives up the property that cost bought.
- **Have the merged agent dispatch a child to verify**: rejected — that is
  exactly the depth-2 joint ADR-0015 removed after it lost verdicts three times.

## Consequences

- **find ≠ verify independence becomes a discipline, not a mechanism.** Stage C
  shares a context with Stage A and can see its reasoning. This is the accepted
  risk of this ADR, and it is the property ADR-0015 rejected "self-verify" to
  protect. The `file:line` citation makes a code-blind refutation visible; it
  does not make one impossible.
- **The stamp is no longer bound to a tree.** With two dispatches, `.finder-hash`
  bound it: a parent edit between them yielded no stamp. With one, a parent that
  edits *while the agent runs* gets a stamp for a tree the agent never read.
  Hashing dispatch → completion cannot close it: ADR-0022 tried both ends and
  each was voided by the agent's own scratch files, because the agent holds
  `Bash`. Stated rather than papered over, as ADR-0019 did with its own residual
  gap. The exposure is narrow — the parent is required to wait on the dispatch,
  not work during it.
- **`review-diff` step 0 loses its second half.** What it said about the *gate*
  was that the pairing window spans two dispatches and does not narrow with the
  flag; there is no window left to reason about, and the stamp keys on
  `SubagentStop` either way. The unresolved observation about
  `CLAUDE_AUTO_BACKGROUND_TASKS` stays exactly where it is: AGENTS.md's Delegation
  section names step 0 as the one place it is recorded, and moving it would buy
  nothing but a dangling pointer.
- **ADR-0014's eval obligation applies in full**, unlike ADR-0019 which only
  deleted a mode. This changes how findings are judged, which is the most
  load-bearing edit `review-diff` can take. The run gates the change: if the
  merged pipeline loses expected findings, or over-reports on the benign
  fixtures, against `results/2026-07-29-briefing-skeleton.md` and beyond
  single-run noise, this decision is reverted rather than shipped. That baseline
  is comparable because the agent definitions and Steps 1–4 of the skill are
  unchanged since it was measured; only the parent's dispatch prose moved.
- Supersedes ADR-0015's *mechanism* for both pipelines. Amends ADR-0022: its
  pairing half is moot, its `SubagentStop`-not-`PostToolUse` half stands and is
  now the entire gate.
- Two fewer agent definitions, two fewer hook files, one fewer settings matcher,
  three fewer markers — and with them the three `permissions.deny` pairs and the
  `.gitignore` entries those markers required.
- **The fork this shape came from could not run the gating eval, and that is why
  it runs here.** Its eight review fixtures are context-dependent modification
  patches against template files the fork deleted, so `git apply --check` fails on
  all eight; its own record states the obligation is deferred rather than
  discharged. In this repository the same fixtures apply cleanly, and the
  baselines were measured against them. Making the fixtures fork-portable is a
  real and separate problem: rebuilding them re-baselines every fixture, which
  would destroy the comparison this decision is gated on, so it must not be done
  in this change.
