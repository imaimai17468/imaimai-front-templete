# 0023. Tags reach what paths cannot; instruction documents get edges, not KB entries

- Status: accepted
- Date: 2026-07-30

> **Note (2026-07-30):** the Decision below states a tag count and list current as
> of its writing. `aegis-share/source/tag-mappings.json` is the live authority for
> which tags exist and how many — treat the Decision's numbers and list as a
> point-in-time snapshot, not a running total, and do **not** add another note like
> this one when tags are later added or removed; the reach test below is what
> governs each new mapping. (This note was itself prompted by adding a mapping
> under that test shortly after the ADR was written — and its first draft named the
> new ordinal, which would have gone stale on the next addition in exactly the way
> the Decision's count did.)

## Context

Two halves of Aegis were unused, both setup gaps rather than decisions.

ADR-0021 recorded the first as a Consequence: `manifest.json` had
`includes_tag_mappings: false`, so `aegis_get_known_tags` returned `[]` and the
`expanded` half of `aegis_compile_context` could never fire. Passing
`intent_tags: []` looked like a choice when it was the only available outcome —
which is how a 2026-07-29 session concluded that Aegis "returned nothing unique"
and proposed deleting it, having measured a misconfiguration rather than the tool.

The second was a `compile_miss` observation from the same day: no path edge
existed from `AGENTS.md` or `.claude/rules/**`, so editing an instruction document
compiled context unrelated to its content. Measured again on 2026-07-30 with
`target_files: ["AGENTS.md"]`: every document returned came from the `review`
*command* edge, and the path contributed nothing.

The observation named `.claude/rules/authoring.md`, which no longer exists — its
content moved into AGENTS.md, which is loaded every session. That narrows the gap
from what the observation described: the authoring *rules* are already in context.
What is missing is the *decisions about* those files.

## Decision

**Tag mappings live in `aegis-share/source/tag-mappings.json`** (entries are
`{tag, doc_id, confidence, source}`), published by the share pipeline like the
rest of `source/`. Seven tags ship: `secrets`, `records`, `gates`, `deployment`,
`dependencies`, `layering`, `delegation`.

**A mapping earns its place only if some real compile exists where no path or
command edge already surfaces that document** — concretely: a plausible
`target_files` whose paths have no edge to it, under a `command` that has no edge
to it either. Only `scaffold`, `refactor` and `review` are ever passed in this
repository, so "some command" means one of those three, not a hypothetical one.

The looser reading — "the tag reaches it somehow" — is what the first draft used,
and it let through `records` → `adr-0008` when all three commands already reach
`adr-0008` at priority 100. That mapping was removed. The test has teeth only if
applied per mapping rather than per tag: `delegation` survives because `review`
reaches neither `adr-0006` nor `adr-0012`, and `layering` survives because
`adr-0016` names `.claude/rules/react.md` as the companion holding its
module-placement rules while no edge connects the two.

Duplicating an existing edge as a tag adds vocabulary without adding reach, and a
catalog too large to hold in mind stops being used. Verified: a compile on
`.github/workflows/ci.yaml` (no path edge at all) under `command: "refactor"` with
`["secrets", "deployment"]` returned 3 base documents — all three via `refactor`
command edges — plus **5 expanded**, each attributed to its tag.

**Instruction documents get path edges to the decisions that govern them, and are
not themselves added to the knowledge base.** `AGENTS.md` → ADR-0008 (it is the
single always-on instruction file, and re-adding detailed rule files was rejected)
and ADR-0021 (records belong in the KB, not here) — both are mistakes
re-introducible by editing that exact file. `.claude/rules/**` → ADR-0008, whose
2026-07-25 amendment is specifically about why those path-scoped files exist.
`.claude/skills/**` → ADR-0006 (skills are sub-steps, never parallel
orchestrators); only three named skills had edges before.

This keeps ADR-0008 item 2 ("the KB carries ADRs only") intact, closing the
`expanded` Consequence ADR-0021 left open.

## Alternatives considered

- **Relax the ADR-only policy so the rule files are served for edits to
  themselves**: the observation's other suggestion, rejected. `AGENTS.md` and
  `.claude/rules/` are already in the prompt when they apply — always-on for the
  former, path-scoped for the latter — so serving them again would return content
  the reader already has, and would put two copies of a live rule under two
  different update disciplines. ADR-0008 item 2 exists for that reason.
- **A tag per document, mirroring the edges**: rejected by the reach test. It
  doubles the vocabulary and adds nothing a path edge does not already supply.
- **Leave the catalog empty and rely on the server-side SLM tagger**: rejected —
  the tagger infers tags from `plan` and still resolves them through
  `tag_mappings`, so an empty table makes it inert too.

## Consequences

- `intent_tags` becomes a real choice, and `[]` becomes a real one too. AGENTS.md's
  step 2 now names the file and states the reach test, so the catalog has a stated
  growth rule rather than accreting.
- The seven tags are a starting vocabulary chosen from this project's recurring
  work, not a taxonomy. Expect to add and retire them; the reach test is what
  keeps that honest.
- `confidence` is set by hand (1.0 where the tag is squarely the document's
  subject, 0.7–0.8 where it is secondary). Nothing validates those numbers, so
  they are an ordering hint, not a measurement.
- A fork that drops `tag-mappings.json` silently returns to the inert state.
  `manifest.json`'s `includes_tag_mappings` is the one-field check.
