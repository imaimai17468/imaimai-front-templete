# 0022. The review stamp keys on `SubagentStop`, not on the dispatch returning

- Status: accepted
- Date: 2026-07-30

## Context

ADR-0015 unnested the verifier and stated that **`review-verifier`'s completion
stamps the commit gate**. ADR-0019 rested the whole single-pass design on that
same sentence. The implementation never did it: `post-agent-review-stamp.sh` was
registered on `PostToolUse(Agent)`.

`PostToolUse` fires after a tool call *succeeds*, and the Agent tool's call
succeeds as soon as the subagent is launched — background execution has been the
platform default for subagents since Claude Code 2.1.198, and the tool returns
launch metadata rather than a result. Measured across this project's transcripts
on 2026-07-30: 122 Agent results, every one of them `status: "async_launched"`,
`isAsync: true`, with a body reading "Async agent launched successfully". The
harness has a separate event for what the ADRs meant — `SubagentStop`, "when a
subagent finishes" — carrying `agent_type`, `agent_id` and
`last_assistant_message`.

So the gate certified dispatch, not review. Launching `code-reviewer` wrote the
`.finder-done` diff hash and launching `review-verifier` wrote `.review-stamp`,
in both cases before either agent had read a line of the diff. Two Agent calls in
sequence unlocked `git commit`.

This was found by investigating a narrower symptom. On 2026-07-29 a
`review-verifier` stalled and produced no verdicts, yet the commit gate was
stamped; that was recorded as "the stamp hook does not check whether the dispatch
failed", and the intended fix was to copy the `tool_response.isError` check that
`post-aegis-compile.sh` already performs. That diagnosis was wrong in a way worth
recording: there was no error to detect. The launch had succeeded, which is all
`PostToolUse` was ever told about. A stalled verifier stamping the gate was not an
unhandled edge case — it was the mechanism working as wired.

ADR-0013 requires gates to key on deterministic artifacts rather than on trust in
the orchestrator. This gate did key on an artifact; the artifact just recorded the
wrong event.

## Decision

A stamp requires two independent facts. They are observable at different moments,
so **each is gathered where it is actually observable**, and the stamp requires
both:

| Fact | Where | Artifact |
|---|---|---|
| the parent did not edit between the two agents (ADR-0015 pairing) | between the finder's **completion** and the verifier's **dispatch** — the window the parent controls | `.finder-hash`, re-sampled and compared at the verifier's dispatch → `.pair-ok` |
| both agents actually finished | `SubagentStop` | `.finder-done`, then `.review-stamp` |

- **`post-agent-review-stamp.sh` moves to `SubagentStop`.** `code-reviewer`'s stop
  writes `.finder-done` and records `.finder-hash`; `review-verifier`'s stop writes
  `.review-stamp` only if `.finder-done` and `.pair-ok` both exist, then consumes
  the cycle's markers. The comparison itself lives in the new
  `pre-agent-review-pair.sh`, at the verifier's dispatch.
- **The compared window contains neither agent's own execution, and getting that
  right took three attempts.** Both review agents hold `Bash` and run experiments
  in the repository, so any window containing an agent's run is voided by that
  agent's own scratch files rather than by anything the parent did. Sampling at the
  verifier's *completion* included the verifier's run; sampling at the finder's
  *dispatch* included the finder's. Both failed against real reviews of this very
  change. `[finder completion, verifier dispatch]` includes neither. The shared
  `lib-review-hash.sh` holds the one hash definition, because two copies would be
  two chances for a drift that never fails loudly — it only refuses every commit.
- **A failed pairing says so, at the verifier's dispatch**, instead of surfacing as
  a commit refused minutes later with no stated cause.
- **Which role finished comes from the invocation argument, not the payload.**
  `.claude/settings.json` registers the stamp script twice, once per matcher
  (`code-reviewer` → `finder`, `review-verifier` → `verifier`), so the harness's own
  agent-type matching is the single place the mapping lives, and
  `scripts/test-review-gate.py` asserts that wiring against the real settings file.
  `agent_type` is read only as a fallback: 20 of 23 `SubagentStop` payloads captured
  on 2026-07-30 carried `agent_type: ""` (unrelated harness-internal subagents), so
  it is not a field to depend on — even though both pinned agents do populate it,
  which an earlier version of this ADR wrongly claimed they did not.
- **The hook refuses any other event.** If `hook_event_name` is not `SubagentStop`
  it writes no marker and warns, naming the event it got. A `PostToolUse` payload
  carries the agent's type under a different key, so a script reading either field
  would silently resume stamping at launch — one settings edit away, and this makes
  that edit loud instead of invisible.
- **The filename does not change.** ADR-0013, ADR-0015 and ADR-0019 each name
  `post-agent-review-stamp.sh`, and an ADR is never rewritten (AGENTS.md, "ADR
  form"), so a rename would leave three records citing a path that does not
  exist. The file's header states which event it is registered on.

The sidechain check is dropped from the stamp path. `SubagentStop` fires about a
child that stopped, so testing a transcript for `isSidechain` would either skip
every legitimate stamp or test nothing, and what it guarded is now moot: the four
pinned review agents hold no `Agent` tool, so a review cannot nest inside a
review. Both `PreToolUse` hooks keep their own check, where the reasoning (a review
launched from inside a subagent must not touch the parent's markers) still applies.

The two new markers, `.finder-hash` and `.pair-ok`, are added to `.gitignore`
in the same change. That is not housekeeping: an un-ignored marker enters the
working-tree hash, so writing it would change the value it is about to be compared
against, and the gate would never stamp.

`scripts/test-review-gate.py` drives dispatch and completion as separate events
through the real hooks, and pins what this decision turns on: a launch-shaped
payload writes no marker and reports the mis-registration; a verifier with no
finder dispatch cannot pair; a parent edit between the two dispatches breaks the
pairing and says so; and — the case the earlier design got wrong — **a file
appearing and disappearing inside the repository during an agent's own run leaves
the pairing intact.** It also asserts the `settings.json` matcher→role wiring
itself, because that mapping is exactly what no test previously covered.

This amends ADR-0015 and ADR-0019 on one point of fact: the sentence "its
completion stamps the commit gate" describes this ADR's implementation, not the
one those ADRs shipped with. Their reasoning is unchanged and was always written
against completion.

## Alternatives considered

- **Keep `PostToolUse(Agent)` and inspect `tool_response`**: rejected, and it was
  the original plan. There is nothing in a successful launch response to inspect —
  no field distinguishes "this agent will produce a verdict" from "this agent will
  stall". The check would have looked like a fix and changed nothing.
- **Have the verifier write the stamp itself as its last action**: rejected — the
  agent would be certifying itself, and ADR-0013 exists because gates must not
  depend on an agent choosing to perform a step. It would also need `Write`,
  which the review agents deliberately lack.
- **Have the parent write the stamp after reading the verdicts**: rejected for the
  same reason one step further out. The parent is the party the gate constrains.
- **Poll for subagent completion from the `Stop` hook**: rejected — it reintroduces
  transcript inspection to answer a question `SubagentStop` answers directly.
- **Refuse to stamp when the verifier's `last_assistant_message` is blank**:
  built, then removed, and now known to be implementable. An agent that stopped
  without reporting has verified nothing, so the check is well-motivated. It was
  removed while the field's behaviour was unobserved, because this change had
  already shown what an unverified payload assumption costs and a gate that wedges
  every commit is worse than the narrow hole it closes. A `review-verifier` payload
  has since been captured carrying a 19,525-character `last_assistant_message`, so
  the objection no longer holds — but adding the check back belongs in its own
  change with its own validation, not bolted onto the one that removed it. That
  change landed on 2026-07-31; see the Residual gap consequence below for the shape
  it took.
- **Additionally require the verifier's report to parse as the expected verdict
  schema**: rejected. It makes the gate a content judge, and schema drift would
  then block every commit.

## Consequences

- The stamp now means what three ADRs already claimed it meant. A stalled,
  killed, or never-reporting verifier leaves the commit blocked.
- **The gate got strictly stricter, and existing habits may now block.** Any flow
  that dispatched the two agents and moved on without waiting for both to finish
  used to earn a stamp and no longer does. That flow was never valid — AGENTS.md
  already requires the parent to wait on both depth-1 dispatches — but it used to
  be silently survivable.
- Wiring correctness is self-testing: if the `SubagentStop` matcher does not fire,
  no stamp appears and the next commit is refused. The failure mode is a blocked
  commit, never a false pass.
- **Residual gap — closed 2026-07-31.** As written, `SubagentStop` proved an agent
  finished but not that it said anything, so a verifier that died mid-run still
  stamped if it stopped after a finder ran on the same diff. That happened on
  2026-07-30: a `review-verifier` died on an API 529 and the gate was stamped with
  no verdict. The blank-report check was then added — the verifier branch now
  refuses to stamp when `last_assistant_message` is present but blank, and stamps
  with a warning when the field is absent entirely, so a platform that does not
  supply it cannot wedge every commit. `scripts/test-review-gate.py` pins both
  outcomes. What remains open is narrower and unchanged: `SubagentStop` still cannot
  prove the agent produced a *real* review. The finder/verifier independence
  (ADR-0015) is what makes the report worth something, and that rests on the pinned
  agent definitions, not on this hook.
- **The lesson generalises past this hook.** `PostToolUse` was assumed to mean
  completion; then, while fixing that, `agent_type` was assumed to be populated for
  every relevant event — an assumption a later, larger capture only partially
  contradicts (populated for both pinned agents; genuinely empty on 20 unrelated
  events) without ever settling why the first version failed. Hook payload
  behaviour belongs in `scripts/test-review-gate.py` as cases built from captured
  payloads, not from the documentation's field list.
- **A hook script registered without the executable bit is silently dead**, and
  `pre-agent-review-pair.sh` shipped that way for one cycle: created 644 while every
  sibling is 755, so the harness — which invokes registered hooks by bare path —
  could not run it, `.pair-ok` never appeared, and no commit could be stamped. This
  is the "gate silently off" failure ADR-0013 exists to prevent, and
  `scripts/test-review-gate.py` masked it by construction, invoking hooks as
  `bash <path>`, which ignores mode bits. It now reads the real `settings.json` and
  asserts every project-local hook command is executable.
- **Cost, recorded because it was substantial.** Four review cycles: three failed to
  stamp, each for a different reason (the wrong event, then two wrong windows, plus
  the missing executable bit). None was wasted — they produced ten confirmed
  findings, several of them false claims this ADR's own author had written about the
  mechanism while changing it. The recurring fault was one habit: describing hook
  behaviour from documentation rather than from an observed payload or an executed
  path, then documenting the description instead of the behaviour.
- The 2026-07-29 memory note that framed this as a missing `isError` check is
  superseded by this ADR; the diagnosis, not just the fix, was wrong.
