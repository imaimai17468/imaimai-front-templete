# Information leakage

Draws on chapter 21 (情報漏えい).

Information leaks when the Worker sends a caller more than that caller needs: a field of someone else's row, an exception message that quotes a query, a hint that an account exists, a file nobody meant to publish. The test for each value is whether this caller needs it now, and the severity depends on what it is (a credential, personal data, the shape of the internals, or only that something exists), who can obtain it, and how many times.

## Where the decision lives here

A value reaches a caller by one of these channels, and each has its own owner:

- **A server function's answer.** The handler in `node_modules/@tanstack/start-server-core/dist/esm/server-functions-handler.js` (version 1.169.31) serializes the result with seroval. An `Error` crosses through TanStack Router's `ShallowErrorPlugin` (`node_modules/@tanstack/router-core/dist/esm/ssr/serializer/ShallowErrorPlugin.js`), which keeps its `message` and drops its name, stack and `cause`. A throw from the validator or the handler lands in the answer's `error` slot with status 200, because `executeMiddleware` in `node_modules/@tanstack/start-client-core/dist/esm/createServerFn.js` catches it into the context; a throw while the body is still being parsed skips that and answers 500 with the serialized `Error` as the whole body, its `message` alone surviving.
- **The server-rendered document.** `setupRouterSsrQueryIntegration` in `src/router.tsx` dehydrates every query in the cache (its default `shouldDehydrateQuery` returns true, `node_modules/@tanstack/router-ssr-query-core/dist/esm/index.js`), with the query's whole `state`, into inline scripts. The router dehydrates each match's `error` as well (`dehydrateMatch` in `node_modules/@tanstack/router-core/dist/esm/ssr/ssr-server.js`).
- **An API route's `Response`**, built by hand in `src/routes/api/`.
- **Workers Logs**, which receive `reportError` (`src/lib/report-error.ts`) records: the event, the error's `message`, its `name` and its `stack`.
- **Static files and bytes users uploaded**, served from `dist/client` and from R2 through `/api/avatars`.

## Checks

**An exception's message never reaches the caller.** The handler sends a thrown `Error`'s `message` whatever produced it, so every defect a server function can raise is a candidate. Here, `dieOnPersistenceError` in `src/shared/gateway/user/index.ts` turns a failed profile read into a defect carrying the original error, `ManagedRuntime.runPromise` rejects with that same value (`causeSquash` in `node_modules/effect/src/internal/effect.ts` returns the first defect as it is), and `getCurrentUserFn` and the read inside `updateProfileResult` both take that path. On 2026-09-30 a `users` row whose `created_at` was set to `'abc'` in local D1 made `getCurrentUserFn` answer 200 with `Expected a valid Date` at `["createdAt"]` in the `error` slot, the message of the decode failure inside `findProfile`. A D1 failure on the same read is a `DrizzleQueryError`, whose message is `Failed query:`, the SQL text, and the bound parameters (`node_modules/drizzle-orm/errors.js`), so the caller would see the table's column names and their own user id; that exact message was not produced locally, because no local D1 change was found that fails the profile read without failing Better Auth's session read first. Right is every failure the handler can reach caught into a result arm with a fixed message, as the write paths already do through `orNone` and `wroteOneRow`, with the detail sent to Workers Logs. Wrong is a defect whose message someone else wrote, which is every `Effect.die` of a caught cause and every `Effect.promise` over a call that can reject. `CurrentSession` reads the session with `Effect.promise` (`src/lib/auth/session/index.ts`), so a rejection from Better Auth's `getSession` takes the same path with Better Auth's message.

**A request the parser refuses gets a fixed answer.** On 2026-09-30, with the session cookie and `x-tsr-serverFn: true`, `updateProfileFn` answered two malformed JSON bodies with 500 and each parser's own message. `not json` answered `Unexpected token 'o', "not json" is not valid JSON`, which quotes the caller's own bytes back. `{"data":{"name":"x"}}`, valid JSON outside seroval's format, answered `Seroval caught an error during the deserialization process`, the `TypeError` it hit, and seroval's issue-tracker URL, which names the deserializer. Neither carries another user's data. Replacing these messages means rewriting the handler's answer from a request middleware, which this reference did not try. Right, until then, is recording them as accepted and revisiting that where a parser's message could carry more, such as another user's value. Wrong is a new route that parses with its own code and returns the exception message the same way.

**The document carries no error message.** The root loader in `src/routes/__root.tsx` fills `currentUserQueryOptions` on every page. On 2026-09-30, with the same corrupted row, a signed-in request for `/` answered 500, and the HTML held `Expected a valid Date` twice: rendered by the router's default error component, and in the inline script as one serialized `Error` that both the root match's `e` and the `["user","current"]` query's `state.error` refer to. The production build sets that component's `show` state to `false` (`useState(false)` in the built `dist/server/assets/Match-*.js`), so a deployed page renders the heading without the message, but `dehydrateMatch` and `dehydrateQuery` have no build switch, so the script copy ships in every build; that was read from the code and not observed on the built Worker. `shouldRedactErrors` in `@tanstack/query-core` applies only to a query still pending when the stream starts, and a settled error is not redacted. Right is the root loader never throwing a message a caller must not read, which the first check provides. A `dehydrate.shouldDehydrateQuery` on the `QueryClient` that skips errored queries removes only the query's reference, because the root match's `e` still carries the loader's error, so it is not a fix on its own. Wrong is a loader or a query that can fail with a message quoting the store, because the document is served to the person whose request failed and stays in their browser history.

**The document holds only what its reader already owns.** For a signed-in reader, the dehydrated cache holds that reader's own profile, `email` included, and the header menu shows it (`xss.md` checks what each loader puts there). `DOCUMENT_HEADERS` in `src/lib/response-headers.ts` sends `Cache-Control: private, no-store`, which `browser-headers.md` checks, so a shared cache does not hand the page to someone else. Right is every query filled during SSR returning only fields this reader may see. Wrong is a loader that fills another user's data, or an output schema widened for one page, because every page carries the root loader's cache.

**A log line carries the event, not the data.** `reportError` writes the error's message and stack. On 2026-09-30 a local trigger that refused every `users` update made the profile write log, under `user.updateName`, `Failed query: update "users" set "name" = ?, ...` followed by `params:` with the submitted name, the timestamp and the user id. The name is data the user chose and the id is not a secret, which is acceptable. A new write that binds an email, a token or free text is wrong where its failure is reported this way, because the parameters then sit in Workers Logs for the retention the account sets. Right, for such a write, is reporting the event and the error's name with the parameters left out. `authentication.md` holds the rule for credentials in log lines.

**What a response reveals by existing is decided per kind of object.** `access-control.md` holds the choice between 403 and 404 and what a listing, a length or a timing still leaks, and `authentication.md` holds the sign-in answer for an unknown email. Right is a message that says a request failed. Wrong is one that names whether the object was absent or not the caller's, wherever existence is private.

**Only built output is served, and the build holds no map or secret.** `public/` holds `favicon.svg` alone, and on 2026-09-30 `dist/client` after `bun run build` held that file and `assets/`, with no `.map` file; `client-side.md` holds the bundle check for secrets and source maps. `bun run dev` adds `data-tsd-source` attributes naming each component's source file and line to the HTML, which a local developer already has; the production build held none of them the same day. Right is `dist/client` containing only what the build wrote. Wrong is a file copied into `public/` for convenience, such as an export, a backup or a `.env`, because `dist/server/wrangler.json` points `assets.directory` at `../client`, so the file is served as a static asset without passing through any route.

**A redirect sends only its location.** On 2026-09-30, `curl -i http://localhost:5173/profile` without a cookie answered 307 with `location: /login` and no body. `src/lib/response-headers.ts` records that this redirect carries none of the document headers. Right is a redirect with no body and no header that depends on the session. Wrong is a debug header or a partial page attached to a redirect, which a browser hides because it follows the `Location` at once.

**Uploaded bytes are served as uploaded.** `AvatarWriter` checks an avatar's MIME type and leading bytes (`src/lib/storage/avatar-validation.ts`) and stores the file unchanged, so a photo's EXIF block, including any GPS position, stays in the object. Today only the owner can fetch it, because `AvatarReader` ties the key to the caller. That is right while the avatar is private. It becomes wrong the day another user or a public bucket URL can read avatars, unless the upload is re-encoded or stripped of metadata first, and whether a Worker can do that for all four accepted formats was not checked for this reference.

## Reproduce locally

Make the profile read fail on your own row, then read each channel. Run `bun run db:push:local`, start `PORTLESS=0 bun run dev` (it serves `http://localhost:5173`), sign in on `/login`, and find `getCurrentUserFn`'s id as the string `createClientRpc` receives in `curl -s http://localhost:5173/src/shared/gateway/user/read.fn.ts`, which is the path `/_serverFn/<id>` answers on. Run `bunx wrangler d1 execute DB --local --command "update users set created_at = 'abc'"`, which only the local D1 under `.wrangler/state` receives. Replay the GET with `curl`, keeping the cookie and the `x-tsr-serverFn: true` and `Sec-Fetch-Site: same-origin` headers, then save the HTML of `/` with the same cookie and search it for `valid Date`. Undo with `bunx wrangler d1 execute DB --local --command "update users set created_at = updated_at"`.

A 200 whose `error` slot holds `Expected a valid Date` means the defect's message reaches the caller, and a 500 document holding it in its scripts means the SSR channel carries it too. A fixed message in both places means the fix holds. A normal profile means the update did not reach the row the session reads, so check the id, and a plain-text 403 `Forbidden` means the replay lacked `Sec-Fetch-Site`, so neither answer says anything about leakage.

## Fix and pin

Catch each store failure into a result arm with a fixed message at the gateway, send the detail to `reportError` with the event name, and keep `Effect.die` for faults that cannot come from the store or a library. Where a read has no arm a caller could act on, a fixed-message `Error` raised in place of the original cause still keeps the query out of the answer and out of the document.

Pin it where the defect is raised: `src/shared/gateway/user/read.test.ts` drives `readCurrentUser` over `CurrentUserReader.layerNoDeps` with a fake `findProfile`, and its test "should propagate the cause as a defect when the profile read fails" pins today's leaking behaviour. Replace it with one where `findProfile` fails with a marker string in its cause, and assert in one `toStrictEqual` that the exit carries the fixed message and not the marker. For the document, the gateway test is the pin, because a test of the dehydrate option alone passes while the match's `e` still ships the message.
