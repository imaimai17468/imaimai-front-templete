# Information leakage

Draws on chapter 21 (情報漏えい).

Information leaks when the Worker sends a caller more than that caller needs: a field of someone else's row, an exception message that quotes a query, a hint that an account exists, a file nobody meant to publish. The test for each value is whether this caller needs it now, and the severity depends on what it is (a credential, personal data, the shape of the internals, or only that something exists), who can obtain it, and how many times.

## Where the decision lives here

A value reaches a caller by one of these channels, and each has its own owner:

- **A server function's answer.** The handler in `node_modules/@tanstack/start-server-core/dist/esm/server-functions-handler.js` (version 1.169.31) serializes the result with seroval. An `Error` crosses through TanStack Router's `ShallowErrorPlugin` (`node_modules/@tanstack/router-core/dist/esm/ssr/serializer/ShallowErrorPlugin.js`), which keeps its `message` and drops its name, stack and `cause`. A throw from the validator or the handler lands in the answer's `error` slot with status 200, because `executeMiddleware` in `node_modules/@tanstack/start-client-core/dist/esm/createServerFn.js` catches it into the context; a throw while the body is still being parsed skips that and answers 500 with the serialized `Error` as the whole body, its `message` alone surviving.
- **The server-rendered document.** `setupRouterSsrQueryIntegration` in `src/router.tsx` dehydrates every query in the cache (its default `shouldDehydrateQuery` returns true, `node_modules/@tanstack/router-ssr-query-core/dist/esm/index.js`), with the query's whole `state`, into inline scripts. The router dehydrates each match's `error` as well (`dehydrateMatch` in `node_modules/@tanstack/router-core/dist/esm/ssr/ssr-server.js`).
- **An API route's `Response`**, built by hand in `src/routes/api/`.
- **Workers Logs**, which receive `reportError` (`src/lib/report-error.ts`) records: the event, the error's `message`, its `name` and its `stack`, with a failed Drizzle query reduced to its SQL text and the driver's error.
- **Static files and bytes users uploaded**, served from `dist/client` and from R2 through `/api/avatars`.

## Checks

**An exception's message never reaches the caller.** The handler sends a thrown `Error`'s `message` whatever produced it, so every defect a server function can raise is a candidate. Here the gateway's runtime stands between the two: `makeRunHandler` in `src/shared/gateway/runtime.ts` runs each handler with `runPromiseExit`, and on any failure, whether a defect the handler raised or one raised while building its layer, it logs each defect in the cause under `gateway.handlerDefect` and rejects with a `HandlerFailed` whose message is always `The request could not be completed`. `dieOnPersistenceError` in `src/shared/gateway/user/index.ts` still turns a failed profile read into a defect carrying the original error, and `CurrentSession` still reads the session with `Effect.promise` (`src/lib/auth/session/index.ts`), so both reach `makeRunHandler` as defects and leave it as the fixed message. On 2026-09-30 a `users` row whose `created_at` was set to `'abc'` in local D1 made `getCurrentUserFn` answer 200 with `Expected a valid Date` at `["createdAt"]` in the `error` slot before that change, and with `The request could not be completed` after it, under `bun run dev` and on the built Worker alike. Right is every server function's handler running through `makeRunHandler`: `git grep -n 'createServerFn' -- src` lists them, and on 2026-09-30 `getCurrentUserFn`, `updateProfileFn` and `uploadAvatarFn` all did. The `/api/avatars` route (`src/routes/api/avatars.ts`) runs its handler through `runAvatarHandler`, which `makeRunHandler` built, so its 500 carries the same fixed message. Right as well is a failure a caller can act on caught into a result arm with its own fixed message, as the write paths do through `orNone` and `wroteOneRow`. Wrong is a handler that calls `Effect.runPromise` or `ManagedRuntime.runPromise` itself, or a plain `async` handler that awaits a store or a library, because its rejection reaches the answer with a message someone else wrote. A `DrizzleQueryError`'s message is `Failed query:`, the SQL text, and the bound parameters (`node_modules/drizzle-orm/errors.js`), which is what such a handler would send.

**A request the parser refuses gets a fixed answer.** On 2026-09-30, with the session cookie and `x-tsr-serverFn: true`, `updateProfileFn` answered two malformed JSON bodies with 500 and each parser's own message. `not json` answered `Unexpected token 'o', "not json" is not valid JSON`, which quotes the caller's own bytes back. `{"data":{"name":"x"}}`, valid JSON outside seroval's format, answered `Seroval caught an error during the deserialization process`, the `TypeError` it hit, and seroval's issue-tracker URL, which names the deserializer. Neither carries another user's data. Replacing these messages means rewriting the handler's answer from a request middleware, which this reference did not try. Right, until then, is recording them as accepted and revisiting that where a parser's message could carry more, such as another user's value. Wrong is a new route that parses with its own code and returns the exception message the same way.

**The document carries no error message.** The root loader in `src/routes/__root.tsx` fills `currentUserQueryOptions` on every page, so a failed read reaches the HTML through the rejection `makeRunHandler` produces. On 2026-09-30, with the same corrupted row, a signed-in request for `/` answered 500. Before the runtime change the HTML held `Expected a valid Date`, rendered by the router's default error component and in the inline script as one serialized `Error` that both the root match's `e` and the `["user","current"]` query's `state.error` refer to. After it, the same two places held `new Error("The request could not be completed")` and the HTML held neither `valid Date` nor `createdAt`, under `bun run dev` and on the built Worker (`bun run build`, then `wrangler dev -c dist/server/wrangler.json`, which this repository used then). `dehydrateMatch` and `dehydrateQuery` have no build switch, and `shouldRedactErrors` in `@tanstack/query-core` applies only to a query still pending when the stream starts, so the fixed message at the runtime is what keeps the script clean. A `dehydrate.shouldDehydrateQuery` on the `QueryClient` that skips errored queries removes only the query's reference, because the root match's `e` still carries the loader's error, so it is not a fix on its own. Right is a loader that reads only through server functions whose handlers run through `makeRunHandler`. Wrong is a loader or a query that can fail with a message quoting the store, because the document is served to the person whose request failed and stays in their browser history.

**The document holds only what its reader already owns.** For a signed-in reader, the dehydrated cache holds that reader's own profile, `email` included, and the header menu shows it (`xss.md` checks what each loader puts there). `DOCUMENT_HEADERS` in `src/lib/response-headers.ts` sends `Cache-Control: private, no-store`, which `browser-headers.md` checks, so a shared cache does not hand the page to someone else. Right is every query filled during SSR returning only fields this reader may see. Wrong is a loader that fills another user's data, or an output schema widened for one page, because every page carries the root loader's cache.

**A log line carries the event, not the data.** `reportError` writes the error's message and stack, except for a `DrizzleQueryError`, whose record takes the SQL text and the driver's error in their place, because Drizzle's own message and stack end in `params:` and the bound values. On 2026-09-30 a local trigger that refused every `users` update made the profile write log, under `user.updateName`, `Failed query: update "users" set "name" = ?, ...` and `Error: D1_ERROR: probe: SQLITE_CONSTRAINT`, with neither the submitted name nor the user id anywhere in the dev server's output. Other errors are logged as they are: a `SchemaError` from Effect's default formatter names the path and what was expected, and not the value, unless the decode call passes the `reportInput` parse option, and a library's own error carries whatever its author wrote. Right is a new store wrapper whose message quotes its inputs getting its own branch in `errorReport`, pinned in `report-error.test.ts`. Wrong is a new write that binds an email, a token or free text and fails through a wrapper `errorReport` passes through unchanged, because the parameters then sit in Workers Logs for the retention the account sets. `authentication.md` holds the rule for credentials in log lines.

**What a response reveals by existing is decided per kind of object.** `access-control.md` holds the choice between 403 and 404 and what a listing, a length or a timing still leaks, and `authentication.md` holds the sign-in answer for an unknown email. Right is a message that says a request failed. Wrong is one that names whether the object was absent or not the caller's, wherever existence is private.

**Only built output is served, and the build holds no map or secret.** `public/` holds `favicon.svg` alone, and on 2026-09-30 `dist/client` after `bun run build` held that file and `assets/`, with no `.map` file; `client-side.md` holds the bundle check for secrets and source maps. `bun run dev` adds `data-tsd-source` attributes naming each component's source file and line to the HTML, which a local developer already has; the production build held none of them the same day. Right is `dist/client` containing only what the build wrote. Wrong is a file copied into `public/` for convenience, such as an export, a backup or a `.env`, because the Worker serves the client build output as static assets, so the file is served without passing through any route.

**A redirect sends only its location.** On 2026-09-30, `curl -i http://localhost:5173/profile` without a cookie answered 307 with `location: /login` and no body. `src/lib/response-headers.ts` records that this redirect carries none of the document headers. Right is a redirect with no body and no header that depends on the session. Wrong is a debug header or a partial page attached to a redirect, which a browser hides because it follows the `Location` at once.

**Uploaded bytes are served as uploaded.** `AvatarWriter` checks an avatar's MIME type and leading bytes (`src/lib/storage/avatar-validation.ts`) and stores the file unchanged, so a photo's EXIF block, including any GPS position, stays in the object. Today only the owner can fetch it, because `AvatarReader` ties the key to the caller. That is right while the avatar is private. It becomes wrong the day another user or a public bucket URL can read avatars, unless the upload is re-encoded or stripped of metadata first, and whether a Worker can do that for all four accepted formats was not checked for this reference.

## Reproduce locally

Make the profile read fail on your own row, then read each channel. Start `PORTLESS=0 bun run dev` (it serves `http://localhost:5173`), sign in on `/login`, and find `getCurrentUserFn`'s id as the string `createClientRpc` receives in `curl -s http://localhost:5173/src/shared/gateway/user/read.fn.ts`, which is the path `/_serverFn/<id>` answers on. Stop `bun run dev`, run `sqlite3 <dev D1 file> "update users set created_at = 'abc'"` (`SKILL.md` names the file, which only the local D1 is), and start `bun run dev` again. Replay the GET with `curl`, keeping the cookie and the `x-tsr-serverFn: true` and `Sec-Fetch-Site: same-origin` headers, then save the HTML of `/` with the same cookie and search it for `valid Date`. Undo the same way with `sqlite3 <dev D1 file> "update users set created_at = updated_at"`.

A 200 whose `error` slot holds `The request could not be completed`, and a 500 document holding that message and no `valid Date` in its scripts, mean the fix holds. `Expected a valid Date` in either place means a handler's defect reached the caller without passing `makeRunHandler`, so find which server function answered and how its handler runs. The dev server's terminal shows the cause under `gateway.handlerDefect`. A normal profile means the update did not reach the row the session reads, so check the id, and a plain-text 403 `Forbidden` means the replay lacked `Sec-Fetch-Site`, so neither answer says anything about leakage.

## Fix and pin

Run each server function's handler through `makeRunHandler`, which logs a defect under `gateway.handlerDefect` and rejects with the fixed message. Catch a store failure a caller can act on into a result arm with its own fixed message at the gateway, and send the detail to `reportError` with the event name.

`src/shared/gateway/runtime.test.ts` pins the runtime: a handler that dies and a layer that dies each reject with exactly `The request could not be completed` and log the defect's own record. `src/shared/gateway/user/read.test.ts` pins the read end to end over `CurrentUserReader.layerNoDeps` with a fake `findProfile` that fails with a `DrizzleQueryError` carrying a marker parameter: the answer is the fixed message, and the one logged record holds the SQL text and not the marker. For the document, those tests are the pin, because a test of the dehydrate option alone passes while the match's `e` still ships the message.
