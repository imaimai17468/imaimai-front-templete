# Deployment and runtime configuration

Draws on chapter 24 (Webサーバーとデプロイ).

What an attacker reaches after the code is right depends on how it is deployed: which hostnames answer, which secrets the runtime holds, what the build leaves beside the bundle, and which limits stop a request that runs long. On Workers most of the book's server layer belongs to Cloudflare, so the review moves to the files that configure what Cloudflare runs, and to the gap between those files and the deployed account, which the repository cannot show.

## Where the decision lives here

- **`alchemy.run.ts`** is the whole runtime configuration: the `App` declaration's `main: "src/ssr.tsx"`, `compatibility` with date `2026-07-15` and `nodejs_compat`, one D1 binding (`DB`) and one R2 binding (`AVATARS_BUCKET`), and `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` as `Config.Redacted`. It sets no `observability`, no `workersDev`, no `routes` or `domain`, no `limits` and no stage-specific branch, so each of those takes the default Alchemy's Worker gives it (`node_modules/alchemy/src/Cloudflare/Workers/Worker.ts`).
- **`docs/DEPLOYMENT.md`** is the procedure: `bun run deploy` (`alchemy deploy`) with a stage, secrets read from the environment it runs in, rollback, and the warning that a rollback leaves D1's schema where it was. Deploying, any `alchemy` command that reaches a Cloudflare account, and `bun run db:push` against the remote D1 are the user's, so a review reads this file and runs none of them.
- **`.gitignore`** keeps `.env*`, `.dev.vars*`, `/dist`, `.wrangler` and `.alchemy/` out of git, and `.env.local.example` lists the variable names with placeholder values.

## Checks

**Every secret is a secret, and no value is a var.** Read the `App` declaration's `env` in `alchemy.run.ts`. Alchemy binds a `Config` value as `secret_text` and a plain string literal as `plain_text` (the `env` doc comment in `node_modules/alchemy/src/Cloudflare/Workers/Worker.ts`). Right is what it holds now: each credential a `Config.Redacted` whose value comes from the environment `bun run deploy` runs in. Wrong is a credential written as a string literal, because its value is then committed in `alchemy.run.ts`. `readAuthSecret` (`src/lib/auth/secret.ts`) throws where one of the three is absent, so a missing secret fails requests rather than falling back to a default; `docs/DEPLOYMENT.md` says why that throw is the only detection.

**The build output holds no value it should not.** On 2026-10-08 `find dist -name '*.map'` and `grep -rl sourceMappingURL dist` both printed nothing after `bun run build`, which runs the build `alchemy deploy` runs, so no source map ships to the browser. `alchemy.run.ts` sets nothing about source maps, and Cloudflare documents what it does when set to `true` (maps uploaded for stack traces, not served to visitors) without stating a default ([source maps](https://developers.cloudflare.com/workers/observability/source-maps/)). For the client bundle, Vite inlines only the `import.meta.env` reads that appear in source, and `git grep -n import.meta.env -- src` shows `DEV`, `SSR` and `VITE_GOOGLE_SIGN_IN`, none of them a secret. The name `BETTER_AUTH_SECRET` does appear in `dist/client`, as a getter in Better Auth's environment shim that reads `process.env` and holds no value. Wrong is a new `VITE_` name that carries a credential, because the build writes its value into a file anyone can download.

**Local secret values stay on the machine that built them.** Before the move to Alchemy, `@cloudflare/vite-plugin` wrote `dist/server/.dev.vars` holding the building machine's secret values, and a plugin in `tools/vite-plugins/` deleted it; both are gone. Whether the bundle `alchemy deploy` builds leaves any file holding a local secret value has not been checked. Bun loads `.env.local` into the environment of what `bun run` starts, so a value there can reach the deploy as well, which `docs/DEPLOYMENT.md` marks unverified. Wrong is any file in the deploy's build output that carries a secret's value, because it travels with whatever that output is copied to next.

**Every hostname that reaches the Worker is one you meant.** With no `workersDev`, `routes` or `domain`, Alchemy's Worker defaults `workersDev` to `true`, which serves the Worker on its stable `workers.dev` URL and turns version preview URLs on (`node_modules/alchemy/src/Cloudflare/Workers/Worker.ts`), so a deploy from this file serves the Worker on its `workers.dev` hostname. That hostname is not in the user's zone, so a header, WAF rule or redirect the zone adds is absent there, which matters for `Strict-Transport-Security`, which `browser-headers.md` leaves to the zone. It is the Workers form of the book's application port reachable around the proxy. Which hostnames the deployed Worker answers on, and whether preview URLs are on, was not observed; the user can read both in the dashboard. Right, once a custom domain serves the app, is the `App` declaration naming it and setting `workersDev: false` in `alchemy.run.ts`, so the file states what is exposed.

**The request's host is treated as client input.** Better Auth builds its base URL from the request when no `baseURL` is set. `authentication.md` covers that check and the rate limiter, which is the other place the book's proxy chapter reaches this stack; Better Auth's client IP header is covered there too.

**Limits come from the platform, and the app sets its own where it needs one.** No `limits` block is set, so the Paid plan's default of 30 seconds of CPU per request applies (10 ms on Free), with 128 MB per isolate and a request body cap of 100 MB on Free and Pro zones ([limits](https://developers.cloudflare.com/workers/platform/limits/)). `MAX_AVATAR_BYTES` in `src/lib/storage/avatar-validation.ts` is checked only after the form has been parsed into memory, as `data-processing.md` says, so the platform's body cap is what bounds parsing on every POST, and a 100 MB body is close to the isolate's memory. Wrong is a new endpoint that parses a body without comparing its size with a ceiling of its own first, because the platform's cap is far above anything this app needs.

**Development settings cannot reach a production build.** The switches that differ by build are `import.meta.env.DEV` reads, which Vite replaces with a literal: `emailAndPassword.enabled` and `useSecureCookies`, which `src/lib/auth/options.ts` derives from the `isDevBuild` that `src/lib/auth/better-auth.ts` passes it as `import.meta.env.DEV`, and the dev sign-in arm in `src/lib/auth/sign-in/index.ts`. Right is a production build in which each dev branch folds away; `authentication.md` and `session.md` check the two auth options. Wrong is a runtime flag, such as a var read at request time, that turns a dev behaviour on, because a var can be set on the deployed Worker without a build.

**The local resources cannot be mistaken for production.** `alchemy.run.ts` names no database or bucket id, and `alchemy dev` keeps its D1 and R2 under `.alchemy/` and applies the migrations there. Each stage that `bun run deploy` reaches gets the resources Alchemy creates for it. A review of a fork checks that no stage adopts another stage's production D1 or bucket, because a shared binding gives a less-guarded deploy the same data.

**Schema changes stay reversible.** `docs/DEPLOYMENT.md` says a rollback restores the Worker and not D1, and asks for a destructive migration to be split into an additive step, a code switch, and a later removal. Read each new file in `src/lib/drizzle/migrations/` against that order. A `DROP COLUMN` in the same pull request as the code that stops reading it is wrong, because the rollback that follows a bad deploy then runs old code against a table without the column. Backups and restore were not reviewed here.

**Topics with no counterpart here.** Gunicorn, nginx, bind addresses, a container user, dropped capabilities, a read-only root filesystem and the Docker socket all configure a host or a container, and the repository holds neither: no `Dockerfile` is tracked, and `alchemy.run.ts` declares no container. A health endpoint has none either (`git grep -n -i health -- src/routes` finds nothing); `bun run smoke` boots the Worker under `alchemy dev` and requests its routes in CI, which covers neither the production bundle nor the deployed Worker.

## Reproduce locally

`bun run build` runs the build `alchemy deploy` runs and writes it to `dist/`. Check that a secret value does not reach it: run `BETTER_AUTH_SECRET=sentinel-probe bun run build`, then `grep -rlF sentinel-probe dist`. On 2026-10-08 that printed nothing, `dist/server` held `ssr.js` and `assets/`, `dist/client` held `assets/` and `favicon.svg`, and `find dist -name '*.map'` found none. A match means a value the deploy binds as a secret was inlined into a file, and a match under `dist/client` means anyone can download it.

## Fix and pin

Change runtime configuration in `alchemy.run.ts` and nowhere else, and give each binding added there its member in `src/cloudflare-env.d.ts` in the same change. A secret is added as a `Config.Redacted` entry in `env`, with its value set in the environment `bun run deploy` runs in, as `docs/DEPLOYMENT.md` describes. A setting the deployed account holds, such as a custom domain, is written into `alchemy.run.ts` once it exists, so the next reviewer can read it.

`bun run smoke` pins the headers and the boot of the Worker under `alchemy dev`. `src/lib/auth/secret.test.ts` pins the throw on a missing secret. Nothing pins the absence of source maps or of secrets in the deployed bundle.
