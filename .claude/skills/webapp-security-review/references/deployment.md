# Deployment and runtime configuration

Draws on chapter 24 (Webサーバーとデプロイ).

What an attacker reaches after the code is right depends on how it is deployed: which hostnames answer, which secrets the runtime holds, what the build leaves beside the bundle, and which limits stop a request that runs long. On Workers most of the book's server layer belongs to Cloudflare, so the review moves to the files that configure what Cloudflare runs, and to the gap between those files and the deployed account, which the repository cannot show.

## Where the decision lives here

- **`void.config.ts`** is the runtime configuration the repository writes: the Worker's `name`, `worker.compatibility_date` `2026-07-15` and `nodejs_compat`. Void adds the bindings it infers from imports, `DB` for `void/db` and `STORAGE` for `void/storage`, and Start's default server entry as `main`. **`env.ts`** declares `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` as required server values. Neither file sets `observability`, `workers_dev`, `routes`, or `limits`, so each takes the default `void deploy` gives it, which was not read for this review.
- **`docs/DEPLOYMENT.md`** is the procedure: `bun run deploy` (`void deploy`), secrets set with `void secret put`, rollback, and the warning that a rollback leaves D1's schema where it was. Deploying and every `void` command that reaches a Cloudflare account or a Void platform are the user's, so a review reads this file and runs none of them.
- **`.gitignore`** keeps `.env*`, `.dev.vars*`, `/dist`, `.cloudflare/`, `.wrangler`, `.void/` and `.void-wrangler.jsonc` out of git, and `scripts/setup/placeholders.dotenv` lists the variable names with placeholder values.

## Checks

**Every secret is a secret, and no value is a var.** Read `env.ts` and `worker.vars` in `void.config.ts`. Void refuses a `worker.vars` name that `env.ts` declares as a server value, and stores each server value as an encrypted Worker secret set with `void secret put` (`node_modules/void/docs/guide/env-vars.md`). Right is what they hold now: each credential declared in `env.ts`, and no `worker.vars`. Wrong is a credential written into `worker.vars`, because its value is then committed in `void.config.ts`. `readAuthSecret` (`src/lib/auth/secret.ts`) throws where one of the three is absent, so a missing secret fails requests rather than falling back to a default; `docs/DEPLOYMENT.md` says why that throw is the only detection.

**The build output holds no value it should not.** On 2026-11-21 `bun run build`, which runs the build `void deploy` runs, wrote no map under `dist/client` and 29 each under `dist/server` and `.cloudflare/output/v1/workers/default/bundle`, which hold the Worker's own code, so no source map ships to the browser. Whether `void deploy` uploads the Worker's maps was not checked. `void.config.ts` sets nothing about source maps, and Cloudflare documents what it does when set to `true` (maps uploaded for stack traces, not served to visitors) without stating a default ([source maps](https://developers.cloudflare.com/workers/observability/source-maps/)). For the client bundle, Vite inlines only the `import.meta.env` reads that appear in source, and `git grep -n import.meta.env -- src` shows `DEV`, `SSR` and `VITE_GOOGLE_SIGN_IN`, none of them a secret. The name `BETTER_AUTH_SECRET` does appear in `dist/client`, as a getter in Better Auth's environment shim that reads `process.env` and holds no value. Wrong is a new `VITE_` name that carries a credential, because the build writes its value into a file anyone can download.

**Local secret values stay on the machine that built them.** Void's builds ignore the root `.env` (`node_modules/void/docs/guide/env-vars.md`), and on 2026-11-21 `BETTER_AUTH_SECRET=sentinel-probe bun run build` left the value in no file under `dist` or `.cloudflare`. Bun loads the root `.env` into the environment of what `bun run` starts, so whether `bun run deploy` carries a value from it into the deploy has not been checked. Wrong is any file in the deploy's build output that carries a secret's value, because it travels with whatever that output is copied to next.

**Every hostname that reaches the Worker is one you meant.** `void.config.ts` sets no `workers_dev` or `routes`, and Cloudflare's own default for a Worker with neither is its `workers.dev` URL. What `void deploy` sets in their place was not read, so treat the Worker as reachable on its `workers.dev` hostname until the dashboard says otherwise. That hostname is not in the user's zone, so a header, WAF rule or redirect the zone adds is absent there, which matters for `Strict-Transport-Security`, which `browser-headers.md` leaves to the zone. It is the Workers form of the book's application port reachable around the proxy. Which hostnames the deployed Worker answers on, and whether preview URLs are on, was not observed; the user can read both in the dashboard. Right, once a custom domain serves the app, is `void.config.ts` naming it under `cloudflare` and turning `workers_dev` off, so the file states what is exposed.

**The request's host is treated as client input.** Better Auth builds its base URL from the request when no `baseURL` is set. `authentication.md` covers that check and the rate limiter, which is the other place the book's proxy chapter reaches this stack; Better Auth's client IP header is covered there too.

**Limits come from the platform, and the app sets its own where it needs one.** No `limits` block is set, so the Paid plan's default of 30 seconds of CPU per request applies (10 ms on Free), with 128 MB per isolate and a request body cap of 100 MB on Free and Pro zones ([limits](https://developers.cloudflare.com/workers/platform/limits/)). `MAX_AVATAR_BYTES` in `src/lib/storage/avatar-validation.ts` is checked only after the form has been parsed into memory, as `data-processing.md` says, so the platform's body cap is what bounds parsing on every POST, and a 100 MB body is close to the isolate's memory. Wrong is a new endpoint that parses a body without comparing its size with a ceiling of its own first, because the platform's cap is far above anything this app needs.

**Development settings cannot reach a production build.** The switches that differ by build are `import.meta.env.DEV` reads, which Vite replaces with a literal: `emailAndPassword.enabled` and `useSecureCookies`, which `src/lib/auth/options.ts` derives from the `isDevBuild` that `src/lib/auth/better-auth.ts` passes it as `import.meta.env.DEV`, and the dev sign-in arm in `src/lib/auth/sign-in/index.ts`. Right is a production build in which each dev branch folds away; `authentication.md` and `session.md` check the two auth options. Wrong is a runtime flag, such as a var read at request time, that turns a dev behaviour on, because a var can be set on the deployed Worker without a build.

**The local resources cannot be mistaken for production.** `void.config.ts` names no database or bucket id, and `bun run dev` keeps its D1 and R2 under `.void/` and applies the migrations there. `void deploy` records the ids of the resources it created in `void.lock.json`. A review of a fork checks that no `void.lock.json` or `cloudflare.d1_databases` entry points a less-guarded deploy at another deploy's production D1 or bucket, because a shared binding gives it the same data.

**Schema changes stay reversible.** `docs/DEPLOYMENT.md` says a rollback restores the Worker and not D1, and asks for a destructive migration to be split into an additive step, a code switch, and a later removal. Read each new file in `db/migrations/` against that order. A `DROP COLUMN` in the same pull request as the code that stops reading it is wrong, because the rollback that follows a bad deploy then runs old code against a table without the column. Backups and restore were not reviewed here.

**Topics with no counterpart here.** Gunicorn, nginx, bind addresses, a container user, dropped capabilities, a read-only root filesystem and the Docker socket all configure a host or a container, and the repository holds neither: no `Dockerfile` is tracked, and `void.config.ts` declares no container. A health endpoint has none either (`git grep -n -i health -- src/routes` finds nothing); `bun run smoke` boots the dev server on an empty local D1 and R2 and requests its routes in CI, which covers neither the production bundle nor the deployed Worker.

## Reproduce locally

`bun run build` runs the build `void deploy` runs and writes it to `dist/` and `.cloudflare/output/`. Check that a secret value does not reach it: run `BETTER_AUTH_SECRET=sentinel-probe bun run build`, then `grep -rlF sentinel-probe dist .cloudflare`. On 2026-11-21 that printed nothing, and `find dist .cloudflare -name '*.map'` found maps only beside the Worker's bundle, none under `dist/client`. A match means a value the deploy binds as a secret was inlined into a file, and a match under `dist/client` means anyone can download it.

## Fix and pin

Change runtime configuration in `void.config.ts` and nowhere else. A secret is declared in `env.ts`, with its value set by `void secret put`, as `docs/DEPLOYMENT.md` describes. A setting the deployed account holds, such as a custom domain, is written into `void.config.ts` once it exists, so the next reviewer can read it.

`bun run smoke` pins the headers and the boot of the Worker under the dev server. `src/lib/auth/secret.test.ts` pins the throw on a missing secret. Nothing pins the absence of source maps or of secrets in the deployed bundle.
