# Deployment and runtime configuration

Draws on chapter 24 (Webサーバーとデプロイ).

What an attacker reaches after the code is right depends on how it is deployed: which hostnames answer, which secrets the runtime holds, what the build leaves beside the bundle, and which limits stop a request that runs long. On Workers most of the book's server layer belongs to Cloudflare, so the review moves to the files that configure what Cloudflare runs, and to the gap between those files and the deployed account, which the repository cannot show.

## Where the decision lives here

- **`wrangler.toml`** is the whole runtime configuration: `main = "./src/ssr.tsx"`, `compatibility_date = "2026-07-15"` with `nodejs_compat`, `[observability] enabled = true`, one D1 binding (`DB`, `database_id` all zeros), one R2 binding (`AVATARS_BUCKET`), and `[secrets] required` naming `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. It sets no `vars`, no `routes`, no `workers_dev`, no `limits`, no `upload_source_maps` and no `[env.*]` section.
- **`dist/server/wrangler.json`** is what `bun run build` hands to `wrangler deploy`, generated from `wrangler.toml` by `@cloudflare/vite-plugin`. On 2026-09-30 it carried `"vars":{}`, the same bindings and secrets list, and `"assets":{"directory":"../client"}`.
- **`docs/DEPLOYMENT.md`** is the procedure: `bun run deploy`, secrets registered with `wrangler secret put` before a name is added to `[secrets]`, rollback, and the warning that a rollback leaves D1's schema where it was. Deploying, `wrangler secret put` and `bun run db:push` against the remote D1 are the user's, so a review reads this file and runs none of them.
- **`.gitignore`** keeps `.env*`, `.dev.vars*`, `/dist` and `.wrangler` out of git, and `.env.local.example` lists the variable names with placeholder values.

## Checks

**Every secret is a secret, and no value is a var.** Read `wrangler.toml` and `dist/server/wrangler.json`. Right is what both hold now: each credential named under `[secrets] required`, registered with `wrangler secret put`, and `vars` empty. Wrong is a credential under `[vars]`, because a var's value is written into `wrangler.toml` and committed. `readAuthSecret` (`src/lib/auth/secret.ts`) throws where one of the three is absent, so a missing secret fails requests rather than falling back to a default; `docs/DEPLOYMENT.md` says why that throw is the only detection.

**The build output holds no value it should not.** Run `bun run build`, then `find dist -name '*.map'` and `grep -rl sourceMappingURL dist`; both printed nothing on 2026-09-30, so no source map ships to the browser. `upload_source_maps` is absent, and Cloudflare documents what it does when set to `true` (maps uploaded for stack traces, not served to visitors) without stating a default ([source maps](https://developers.cloudflare.com/workers/observability/source-maps/)). For the client bundle, Vite inlines only the `import.meta.env` reads that appear in source, and `git grep -n import.meta.env -- src` shows `DEV`, `SSR` and `VITE_GOOGLE_SIGN_IN`, none of them a secret. The name `BETTER_AUTH_SECRET` does appear in `dist/client`, as a getter in Better Auth's environment shim that reads `process.env` and holds no value. Wrong is a new `VITE_` name that carries a credential, because the build writes its value into a file anyone can download.

**Local secret values stay on the machine that built them.** `@cloudflare/vite-plugin` 1.54.2 emits `dist/server/.dev.vars` from its `generateBundle` whenever it read the Worker config from a file, with no option to turn it off, and fills it from wrangler's `getVarsForDev`, which with `[secrets]` set reads the project's `.dev.vars`, or, where none sits beside `wrangler.toml`, the `.env` files together with the build's own `process.env`. Before `dropLocalSecrets` (`tools/vite-plugins/drop-local-secrets-plugin.ts`, registered after `cloudflare()` in `vite.config.ts`), a build with `BETTER_AUTH_SECRET` set to a sentinel in the shell wrote the sentinel into that file. The plugin deletes the file from the bundle before Vite writes it, so on 2026-09-30 `dist/server` held `.vite`, `assets`, `index.js` and `wrangler.json`, and the sentinel matched nothing under `dist`. Nothing that ships needs the file: in wrangler 4.110.0 the only callers of `getVarsForDev` are local dev's bindings and `wrangler types`, so `wrangler deploy` never read it, and `bun run smoke` passes its three secrets with `--var`. Running the built Worker locally still works through the process environment: `vp preview` without the file logged `Using secrets defined in process.env` and answered `/login` with 200, because Bun loads `.env.local` into the environment of what it runs. A bare `wrangler dev -c dist/server/wrangler.json` outside Bun gets no secrets and takes them with `--env-file .env.local` or `--var`. Wrong is a `dist/server/.dev.vars` after a build, because that file carries the values of every `[secrets] required` name on the building machine into whatever `dist/` is copied to next, such as a CI artifact or a bug report; `dist/client/.assetsignore` still lists it, which keeps it out of the static assets and nothing more.

**Every hostname that reaches the Worker is one you meant.** With no `routes` and no `workers_dev` key, Wrangler's configuration reference says `workers_dev` defaults to `true` ([configuration](https://developers.cloudflare.com/workers/wrangler/configuration/)), so a deploy from this file serves the Worker on its `workers.dev` hostname. That hostname is not in the user's zone, so a header, WAF rule or redirect the zone adds is absent there, which matters for `Strict-Transport-Security`, which `browser-headers.md` leaves to the zone. It is the Workers form of the book's application port reachable around the proxy. Which hostnames the deployed Worker answers on, and whether preview URLs are on, was not observed; the user can read both in the dashboard. Right, once a custom domain serves the app, is `routes` naming it and `workers_dev = false` in `wrangler.toml`, so the file states what is exposed.

**The request's host is treated as client input.** Better Auth builds its base URL from the request when no `baseURL` is set. `authentication.md` covers that check and the rate limiter, which is the other place the book's proxy chapter reaches this stack; Better Auth's client IP header is covered there too.

**Limits come from the platform, and the app sets its own where it needs one.** No `limits` block is set, so the Paid plan's default of 30 seconds of CPU per request applies (10 ms on Free), with 128 MB per isolate and a request body cap of 100 MB on Free and Pro zones ([limits](https://developers.cloudflare.com/workers/platform/limits/)). `MAX_AVATAR_BYTES` in `src/lib/storage/avatar-validation.ts` is checked only after the form has been parsed into memory, as `data-processing.md` says, so the platform's body cap is what bounds parsing on every POST, and a 100 MB body is close to the isolate's memory. Wrong is a new endpoint that parses a body without comparing its size with a ceiling of its own first, because the platform's cap is far above anything this app needs.

**Development settings cannot reach a production build.** The switches that differ by build are `import.meta.env.DEV` reads, which Vite replaces with a literal: `emailAndPassword.enabled` and `useSecureCookies`, which `src/lib/auth/options.ts` derives from the `isDevBuild` that `src/lib/auth/better-auth.ts` passes it as `import.meta.env.DEV`, and the dev sign-in arm in `src/lib/auth/sign-in/index.ts`. Right is a production build in which each dev branch folds away; `authentication.md` and `session.md` check the two auth options. Wrong is a runtime flag, such as a var read at request time, that turns a dev behaviour on, because a var can be set on the deployed Worker without a build.

**The local resources cannot be mistaken for production.** `database_id` is all zeros and the bucket is `local-avatars`, so the committed file points at no real resource, and `bun run db:push:local` applies migrations to the local D1 under `.wrangler/state`. A fork that deploys fills these in; a review of that fork checks that no production id is shared with a preview or staging Worker, because a shared binding gives a less-guarded deploy the same data.

**Schema changes stay reversible.** `docs/DEPLOYMENT.md` says a rollback restores the Worker and not D1, and asks for a destructive migration to be split into an additive step, a code switch, and a later removal. Read each new file in `src/lib/drizzle/migrations/` against that order. A `DROP COLUMN` in the same pull request as the code that stops reading it is wrong, because the rollback that follows a bad deploy then runs old code against a table without the column. Backups and restore were not reviewed here.

**Topics with no counterpart here.** Gunicorn, nginx, bind addresses, a container user, dropped capabilities, a read-only root filesystem and the Docker socket all configure a host or a container, and the repository holds neither: no `Dockerfile` is tracked, and `wrangler.toml` has no container section. A health endpoint has none either (`git grep -n -i health -- src/routes` finds nothing); `bun run smoke` boots the built Worker and requests its routes in CI, which covers the build rather than the deployed Worker.

## Reproduce locally

Check what the build leaves behind: run `bun run build`, then `ls -a dist/server dist/client` and `cat dist/client/.assetsignore`. No `.dev.vars` in either directory, and `.assetsignore` listing `wrangler.json` and `.dev.vars`, is the state described above. A `.dev.vars` in `dist/server` means `dropLocalSecrets` stopped removing it, such as after the Cloudflare plugin renamed the file or moved where it emits it. A `.dev.vars` inside `dist/client` without the ignore file would mean it is uploaded as a public asset.

Check that a secret value does not reach the browser: run `BETTER_AUTH_SECRET=sentinel-probe bun run build`, then `grep -rlF sentinel-probe dist`. No match is the current state. A match in `dist/server/.dev.vars` is the regression above, and a match under `dist/client` means a value reached a file anyone can download. No match proves nothing where the build did not see the variable, so check that the shell exported it, and confirm the probe once by building with `dropLocalSecrets()` removed from `vite.config.ts`, which puts the sentinel back into `dist/server/.dev.vars`.

## Fix and pin

Change runtime configuration in `wrangler.toml` and nowhere else, run `bun run cf-typegen` after, and let the generated `dist/server/wrangler.json` follow. A secret is added by registering it first and naming it under `[secrets] required` second, in the order `docs/DEPLOYMENT.md` gives. A setting the deployed account holds, such as a custom domain, is written into `wrangler.toml` once it exists, so the next reviewer can read it.

`bun run smoke` pins the headers and the boot of the built Worker, and before it boots anything it exits 1 where the build left `dist/server/.dev.vars`; with `dropLocalSecrets()` removed from `vite.config.ts` it printed `[smoke] the build wrote dist/server/.dev.vars` and failed on 2026-09-30. The plugin writes the file only for a name it finds a value for, and CI holds no secret, so `.github/workflows/ci.yaml` sets `BETTER_AUTH_SECRET` on the smoke step to give that check something to catch on every pull request. `src/lib/auth/secret.test.ts` pins the throw on a missing secret. Nothing pins the absence of source maps or of secrets in `dist/client`; the two commands in *Reproduce locally* are the check until a CI step runs them.
