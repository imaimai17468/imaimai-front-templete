# Input validation

Draws on chapter 10 (入力値検証).

Input validation checks that a value a request delivered is one the feature's specification allows: its type, whether it is present, its length or range, its format, and how it combines with the other fields. Binding a SQL parameter (`sql-injection.md`), escaping on output, and the authorization decision (`access-control.md`) each stop a different failure, and validation replaces none of them. Nothing in a browser enforces anything either, because a server function and an `/api/` route both take a request built by hand.

## Where the decision lives here

The validator of each `createServerFn` decides, in the `*.fn.ts` that declares it. `parseProfileUpdate` and `parseAvatarUpload` in `src/shared/gateway/user/update.fn.ts` decode what the wire delivered with Effect `Schema`: `FormDataSchema` accepts only a `FormData` instance, then `UpdateUserSchema` (`src/shared/entities/user/index.ts`) decodes the `name` entry and `AvatarFileSchema` the `avatar` entry. For a multipart or URL-encoded body the server-function handler builds that `FormData` with `request.formData()` before the validator runs (`node_modules/@tanstack/start-server-core/dist/esm/server-functions-handler.js`).

`UpdateUserSchema` is also the object `standardSchemaResolver` reads in `src/routes/_authed/profile/-components/profile-form/profile-form.tsx`, and `MAX_AVATAR_BYTES` in `src/lib/storage/avatar-validation.ts` is read by both the form's pre-check and `AvatarFileSchema`. So the browser and the server hold one rule per field, and the browser's copy only spares the user a request that would be refused.

Checks that need the caller or a stored row, such as whether an avatar key belongs to the signed-in user, are made in the gateway rather than the validator, and `access-control.md` covers them.

## Checks

**Every entrance decodes its input with a `Schema` before using it.** Run `git grep -n -e 'createServerFn(' -e 'handlers:' -- src`. A server function that takes input is right where `.validator(...)` is handed a function built from `Schema.decodeUnknownSync` (or another `Schema` decode) on the value as `unknown`, as both in `update.fn.ts` are. It is wrong where the validator only annotates a parameter's type, because the annotation is erased and the handler receives whatever was sent. A file route is right where each `searchParams.get`, `request.formData()` or `request.json()` result is decoded or checked before any store is read, in the route or in the gateway it calls, as the avatar `key` from `src/routes/api/avatars.ts` reaches `isOwnAvatarKey` inside `AvatarReader` before the bucket is read. `getCurrentUserFn` in `src/shared/gateway/user/read.fn.ts` takes no input, so it has nothing to validate.

**The browser reads the server's rule rather than a copy of it.** Run `git grep -n -e 'maxLength' -e 'pattern=' -e 'max=' -- src/routes src/shared/components`, which returns nothing on main today. The code is right where a form's limits come from the schema or constant the validator also reads. It is wrong where a limit is written in the component alone, which is the drift where the page stops at 50 characters and the server accepts 5,000.

**Length is counted in the unit the specification means.** `Schema.isMaxLength` compares the string's `.length` (`node_modules/effect/src/Schema.ts`), which counts UTF-16 code units: 26 of 😀 (U+1F600, two UTF-16 units each) are 52 units and fail the 50-character name limit, though a reader sees 26 characters. `File.size` counts bytes. Decide which unit a limit means, and where it means characters a person sees, say so in the schema and test it with a non-ASCII value.

**Each field's normalization is chosen for that field.** `UpdateUserSchema` does not trim, so a name of three spaces decodes unchanged, and `displayName` shows it, since that function falls back only on `""`. Where the specification says a name is not blank, decode through `Schema.Trim`, which strips the ends, and pin with a test that a name of spaces then fails the minimum length. A field whose whitespace is part of the value, as a password's is, is never trimmed; here Better Auth reads the password, so no schema of ours touches it.

**Missing, empty and wrong-typed values are rejected, each with its own reason.** `form.get("name")` returns `null` when the entry is absent and a `File` when a file was sent under that name, and `UpdateUserSchema` answers both with `Expected string`; an empty string fails `Name is required`. No server function here takes a request whose fields are each optional, so absent and empty never need different meanings. A future partial update does, and its schema declares the field optional so that an absent field and an empty one decode to different values.

**A number from a string is decoded, never defaulted.** A query parameter arrives as a string. `Schema.FiniteFromString` answers `abc` with `Expected a finite number` but decodes an empty string to `0`, as `Number("")` does, so `?page=` would silently become page 0. Decode through `Schema.NonEmptyString.pipe(Schema.decodeTo(Schema.FiniteFromString))`, which answers `""` with `Expected a value with a length of at least 1`, and bound the result with `Schema.isBetween`, so a caller's mistake is refused rather than turned into a default. The chapter's trap of a JSON boolean passing an integer check has no counterpart here: `Schema.Number` answers `true` with `Expected number`.

**A finite set of choices is an allow-list.** `Schema.Literals(["newest", "oldest"])` refuses any other string, and a select box on the page restricts nothing a hand-built request sends. A deny-list of dangerous substrings on `name` is wrong: it refuses a legitimate name such as `D'Angelo`, and it misses any spelling it does not list.

**Unknown fields do not reach the write.** `Schema.Struct` drops keys it does not declare unless the decode is given `{ onExcessProperty: "error" }` (`node_modules/effect/src/SchemaAST.ts`), and `parseProfileUpdate` reads only `form.get("name")`, so an added `role` entry never reaches `ProfileWriter`. The columns a write may set are named in `UserRowUpdate` in `src/shared/gateway/user/index.ts`, which is the second guard against a field nobody meant to be writable. Where a JSON contract has to refuse unknown fields rather than drop them, pass that option at the wire.

**One name sent twice has one reading.** `FormData.get` returns the first entry of a repeated name, so `name=first&name=second` stores `first`. That is right while the validator is the only reader. It is wrong where another layer reads `getAll` or the last entry, because the value checked and the value used then differ. Where repetition must be refused, read `getAll` and require one entry.

**A pattern matches the whole value.** `AVATAR_KEY_PATTERN` in `src/lib/storage/avatar-validation.ts` opens with `^` and closes with `$`. A pattern without both accepts any string that merely contains a match. Keep patterns to simple fixed formats, and bound the length before matching, so a long input cannot make a backtracking pattern run for seconds.

**A URL is checked for the use it is put to.** `httpsUrl` in `src/lib/https-url.ts` lets a stored provider image leave the read only as an absolute `https` URL. A value used as a redirect target or fetched by the server needs its own rule, and a URL the server fetches is a server-side request forgery question that validation alone does not settle.

**A rejection says which rule failed and nothing more.** The server-function handler sends a thrown `Error`'s `message` to the client. The messages `Schema` builds name the rule and the path (`Name must be 50 characters or less` at `["name"]`) and leave out the rejected value, because the `reportInput` parse option is off by default. Keep it off at the wire, and keep a hand-written message from quoting the input, so a rejected secret is not reflected back or copied into a log.

## Reproduce locally

Replay the profile write with values just outside the rule. Start `PORTLESS=0 bun run dev` (it serves `http://localhost:5173`), sign in on `/login` as the dev user, and copy from the Network panel the request the profile page's Save button sends to `/_serverFn/...`. Send it again with `curl`, keeping the session cookie and the `x-tsr-serverFn: true` header, and change only the `name` field: 50 `a` characters, then 51, then 26 of U+1F600, then two `name` entries. Read the row with `sqlite3 -readonly <dev D1 file> "select id, name from users"` (`SKILL.md` names the file) after each.

The HTTP status proves nothing here. On 2026-09-30 a 51-character name answered 200, the same status as an accepted one, with the validator's message in the body's `error` slot and no `"updated"` result. What decides it is the body and the row: an `"updated"` result and a row holding the over-long name means the server does not enforce the limit, and a validation message with the row unchanged means it does. The same request without the session cookie answered 200 with `Not authenticated`, which says the validator passed and the gateway refused, and so proves nothing about the limit. The other three sends were replayed the same day: 50 characters answered `"updated"` and the row held them, 26 of U+1F600 answered the length message with the row unchanged, and two entries answered `"updated"` with the row holding the first. A 500 whose body is `{"status":500,"unhandled":true,"message":"HTTPError"}` also proves nothing: on 2026-09-30 every call answered that way after a dev server restart until a page had loaded the `update.fn.ts` module once.

## Fix and pin

Write the rule once, as a schema under `src/shared/entities/` or a constant beside the validator, and have both the form and the `*.fn.ts` read it. Put the decode in the validator, so the handler receives only a decoded value, and leave the checks that need the session to the gateway.

Test the validator directly, as `src/shared/gateway/user/update.fn.test.ts` tests `parseProfileUpdate`, with one row per boundary: the shortest and longest accepted values and one past each end, a non-ASCII value at the limit, whitespace only, the entry missing, a `File` in a text field, a repeated name, an empty numeric parameter where one is decoded, and a legitimate name with an apostrophe such as `D'Angelo`. That last row matters as much as the others, because a fix that rejects apostrophes fails it while every attack row still passes.
