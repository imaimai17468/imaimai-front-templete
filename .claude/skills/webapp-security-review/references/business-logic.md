# Business logic

Draws on chapter 20 (ビジネスロジックの脆弱性).

A business-logic flaw is reached with well-formed requests from the right user, sent in an order, a number or at a time the design did not weigh: a step skipped, an action replayed, two requests racing, a value the server knew taken from the client instead. No payload marks the attack, so no scanner finds it, and the only reference to compare an answer with is a written statement of the rules the feature must keep.

## Where the decision lives here

The rules live in the gateway services that perform the write, because that is the last code to run before the store changes. Two flows write today:

- **The name write.** `ProfileWriter.updateProfile` in `src/shared/gateway/user/update.ts` takes the user from `CurrentUserReader`, the time from `DateTime.now`, and only `name` from the request, then sets one row. It has no state beyond the value, so replaying it sets the same name again and the last write wins.
- **The avatar replace.** `AvatarWriter.replace` in `src/shared/gateway/user/avatar/update.ts` reads the row's current key, puts a new object under a fresh key, points the row at it while the row still holds the key it read, then deletes the previous object. Each step's failure has its own answer, pinned by `src/shared/gateway/user/avatar/update.test.ts`.

The client runs the two as one submission, the upload first and the name second (`createSubmitProfile` in `src/routes/_authed/profile/-components/profile-form/submit-profile.ts`), but each is its own server function, so a caller can send either alone, in either order, as often as they like.

The chapter's worked example, a follow request with states and an approver, has no counterpart here. Its method (write the invariants, draw the state table, then attack each row) is what the next stateful feature starts from,.

## Checks

**Write the invariants before reading the code.** For the avatar they are: the row points at an object that exists, an object in the bucket under `<userId>/avatars/` is either the one the row points at or is logged as left over, and a user's row only ever points at a key with that user's id. For each, name the code that keeps it: the delete runs after the row update, the rollback removes a new object the row never pointed at, and `replace` builds every key from the `userId` it was given. A fourth invariant, that a cleanup deletes only this user's objects, is kept by `isOwnAvatarKey` checking the previous key before it is deleted. Right is every invariant with a line that keeps it. Wrong is one kept only by the form, such as the Save button's `disabled={isPending}`, which a second tab or `curl` skips.

**A value the server can derive never comes from the request.** The avatar key, its extension and the row's `updatedAt` are all built on the server, from `AvatarKeyIds`, the allow-listed MIME type and the clock. `api.md` checks the same rule for owner ids and roles. In a feature with prices, counts or states, right is the server recomputing the value from its own rows, and wrong is the client sending it back and the server checking that it looks plausible.

**Check-then-act on the same row races.** `replace` reads `previousKey`, and two uploads by one user can both read the same one before either writes. `UserAvatarKeys.set` takes that `previousKey` and adds it to the update's `where` clause (`avatar_key = ?`, or `avatar_key is null` where the row held none), through the extra conditions `writeUserRow` in `src/shared/gateway/user/index.ts` and-s with the id. The first write touches one row and deletes the previous object. The second touches zero rows, because the row no longer holds what it read, so `wroteOneRow` logs `user.setAvatarKey` with `expected 1 row, got 0` and the request takes the rollback arm: it deletes its own new object and answers `AvatarUploadFailed`. Right is every write that depends on a value read earlier in the request naming that value in its `where` clause, and a zero-row result handled as the loser's arm. Wrong is a `where` on the row's id alone, because both requests then report one row, the row keeps whichever write landed last, and the other new object stays in the bucket with nothing pointing at it and nothing logged.

**A failure between steps leaves a state someone chose.** `replace` answers each partial state by name: a failed put leaves the row alone, a failed row update removes the new object and logs `AvatarObjectOrphaned` if that delete fails too, and a failed delete of the previous object answers `cleanup: "pending"` with the new avatar in place. The row update is not in one transaction with the R2 put, because D1 and R2 share none, so the order of the steps is what keeps the reference invariant. One case the order does not cover: where D1 commits the update and the Worker still receives an error, the rollback deletes an object the row now points at, and the avatar answers 404. Whether D1 can report a failure for a write it committed was not confirmed for this reference. Right, for a new multi-store flow, is each partial state named in the result type and pinned by a test. Wrong is a flow that assumes an error means nothing changed.

**A rule that cannot be checked refuses the action.** Where `UserAvatarKeys.find` fails, `replace` answers `AvatarUploadFailed` before any put, and where the session read finds no caller, `ProfileWriter` answers `NotAuthenticated`. Right is every new precondition failing closed in the same way. Wrong is a lookup failure treated as "no restriction found", which lets the action through exactly when the store is down.

**Replaying one action has a defined result.** A replayed name write is harmless. A replayed upload stores a second object and deletes the first, which is correct for the row and costs a put each time; `api.md` covers bounding that. A future action with a side effect beyond the row, such as a notification, an email, a counter or a charge, is right where a second identical request produces no second side effect, through a state check in the conditional update or an idempotency key stored with the result in the same write. Wrong is a check that the row already holds the new value, followed by the side effect anyway.

**A rate limit and a business count are two rules.** A limit per minute bounds load. "Once per user" or "once per state" bounds meaning, and a caller within the rate limit can still break it. Neither exists here today, because no action has a count in its meaning yet. Right is each one stated separately in the feature's rules, the count enforced in the conditional update or a unique constraint in `src/lib/drizzle/schema.ts`, and the rate in front of the gateway. Wrong is a rate limit offered as the enforcement of a count.

**A stateful feature arrives with its state table.** The first feature whose rows have a status (an invitation, a request, an order) gets a table of current state, action, actor, next state and whether it is allowed, with the refused rows written out. Right is each row mapped to a condition in the update's `where` clause (state and actor both) and to a test. Right is also re-reading the state a related feature owns at the moment of the final write, such as a block or a deletion that happened after the flow began. Wrong is a status check done on an earlier request, such as the page that showed the confirm button.

## Reproduce locally

Race several uploads by one user against the dev server, then ask the app which objects still exist. Run `bun run db:push:local`, start `PORTLESS=0 bun run dev` (it serves `http://localhost:5173`), sign in on `/login`, upload an avatar once through the profile page, and copy that upload's request to `/_serverFn/...` from the Network panel. From a script, send it five times at once with `curl`, each call backgrounded with `&` and the batch closed by `wait`, keeping the session cookie and the `x-tsr-serverFn: true` and `Sec-Fetch-Site: same-origin` headers. Each answer's `avatarUrl` names the key that request wrote. Request every one of those URLs with the same cookie, and read the row with `bunx wrangler d1 execute DB --local --command "select avatar_key from users"`. The installed wrangler has no `r2 object list`, so the avatar route is the listing: as the owner, a 200 means the object exists and a 404 means it is gone.

Exactly one 200, for the key the row holds, is the expected result whether or not the requests interleaved, so read the answers as well: a request that lost the race answers `"failed"` and leaves a `user.setAvatarKey` line with `expected 1 row, got 0` in the dev server's log. On 2026-09-30, before the conditional update, a batch of two and a batch of five both ended with one 200 and no failure on `bun run dev`. On 2026-10-01, after it, five uploads sent at once with `Promise.all` from the signed-in profile page's console answered two `uploaded` and three `Failed to upload avatar`, the log held three `user.setAvatarKey` lines with `expected 1 row, got 0`, and of the two uploaded keys only the one the row held answered 200 to a `cache: "no-store"` fetch (a cached fetch still answered 200 for a deleted key), so the dev server did interleave that batch. Two or more 200s, with only one of those keys in the row, is the race coming back. A row whose key answers 404 would break the reference invariant, which the order of steps is meant to prevent. Any `"failed"` answer means that request was refused, so read the dev server's log for its event name before counting it.

## Fix and pin

Keep each rule in the gateway write that it governs: a conditional `where` for state and ownership, a unique constraint for "only one", and the step order plus a named result arm for a flow that spans stores.

Pin each rule with the fakes that `src/shared/gateway/user/avatar/update.test.ts` already builds for `AvatarBucket`, `AvatarKeyIds` and `UserAvatarKeys`, one test per row of the state table and per partial failure. Assert in one `toStrictEqual` both the answer and the calls the fakes recorded, as that file's tests do with `removeCalls`, `updateCalls` and `uploadCalls`, so a fix that refuses the action but still performs a side effect fails. For the conditional update, the `AvatarWriter.replace racing another upload` tests give the fakes one shared row and bucket, make `set` a compare-and-set over that row, and run two uploads that both read the old key, once in each order; each asserts that only the winner's object remains and the row names it. They fail where `replace` stops passing the key it read to `set`, or stops rolling back on zero rows. The fakes never reach the SQL, so the `avatarKeyStillHeld` test in the same file renders the condition `set` adds and fails where it stops matching the key, or matches a null with `=`.
