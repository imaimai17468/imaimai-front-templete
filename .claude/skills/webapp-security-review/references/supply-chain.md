# Dependencies and the software supply chain

Draws on chapter 23 (依存ライブラリとソフトウェアサプライチェーン).

Most of the code the Worker runs was written by someone else and reached this repository through a registry, a lockfile, an install step and a CI runner. Each of those is a place where the code that ships can differ from the code anyone reviewed, so a review asks which input decides each piece of the build, and what fails when that input changes without a pull request.

## Where the decision lives here

- **`package.json`** names every direct dependency at an exact version, with no `^` or `~`, and `bunfig.toml` sets `exact = true` so `bun add` keeps writing them that way. `overrides` pins `browserslist`, `vite` and `vitest` for the whole graph. `bun run check:pins` (`scripts/check-toolchain-pins.entry.ts`) fails where the `vite` or `vitest` pin, `@vitest/coverage-v8`, `oxlint`, `oxfmt` or `oxlint-tsgolint` disagrees with what `vite-plus` bundles; the `browserslist` override is compared with nothing.
- **`bun.lock`** records the resolved graph, direct and transitive, with a `sha512-` integrity value per package (1217 of them on 2026-09-30). CI and `bun run setup` both install with `bun install --frozen-lockfile`.
- **`bunfig.toml`** sets `minimumReleaseAge = 604800`, so a version published less than seven days ago is not chosen at resolution. Its comment says the check applies only when resolving, so a version already in `bun.lock` installs whatever its age.
- **`mise.toml`** pins node, bun, actionlint and shellcheck, and CI installs them through `jdx/mise-action`. The repository has no mise lockfile, and how mise verifies the binaries it downloads was not checked here.
- **`.github/workflows/ci.yaml`** is the one workflow. It runs on `pull_request` and on `push` to `main`, sets `permissions: contents: read` at the top, references both actions (`actions/checkout` and `jdx/mise-action`) by full commit SHA with the version in a comment, and holds no deploy step and no secret. Its audit step runs `scripts/audit-dependencies.entry.ts`, which runs `bun audit --json` and fails where an advisory names a direct dependency or where stdout holds no JSON advisory report. Bun 1.3.1 exits 1 both for advisories and for a failed registry request, and on 2026-09-30 an unreachable registry (`BUN_CONFIG_REGISTRY=http://127.0.0.1:9`) left stdout empty, so the step reads the report rather than the exit code, and a registry outage fails the step.
- **`.github/dependabot.yml`** opens weekly version-update pull requests for the `bun` and `github-actions` ecosystems, each held back seven days by `cooldown`.
- **`lefthook.yml`** runs `check:pins`, actionlint and shellcheck on pre-push, the last two only where `mise` is on `PATH`.

## Checks

**The build installs exactly the reviewed lockfile.** Read every install in `ci.yaml` and `scripts/setup.sh`. Right is `bun install --frozen-lockfile` everywhere, which refuses to run where `package.json` asks for something `bun.lock` does not hold. Wrong is a plain `bun install` or a `bun add` in a workflow, because either rewrites the graph on the runner and the build then ships a resolution nobody saw in a diff. A pull request that edits `package.json` without a matching `bun.lock` fails that install. A pull request that edits only `bun.lock` and stays inside the ranges the manifests allow installs cleanly, because the frozen install refuses only a lock it would have to rewrite, so the lock hunk is what a reviewer reads in every pull request that touches it, Dependabot's included: each new transitive package, each moved version and each changed integrity value.

**No dependency runs install scripts without a decision.** Bun runs lifecycle scripts only for packages on its built-in allowlist or named in `trustedDependencies` ([Bun lifecycle docs](https://bun.com/docs/install/lifecycle)). `package.json` has no `trustedDependencies`, and `bun pm untrusted` printed "Found 0 untrusted dependencies with scripts" on 2026-09-30. Adding the key replaces Bun's default list rather than extending it, so a pull request that adds it is right only where it lists every package that still needs its script. Wrong is `bun pm trust --all` to make a failing install pass.

**A new dependency is the package it claims to be.** For each name a pull request adds to `package.json`, open its npm page from the project's own documentation, compare the repository link and the maintainers with the source it claims, and check the name against the spelling in that documentation, because a typosquat differs by one character. Record why the package was chosen over the standard library or an existing dependency in the pull request body. Download counts and stars are not evidence of anything the review needs.

**One registry decides every name.** The repository has no `.npmrc` and `bunfig.toml` sets no registry, so every package resolves from the default npm registry and a private name cannot be shadowed by a public one here. A reviewer's own `~/.npmrc` can still redirect installs on their machine; CI reads none. The code is wrong once a scoped private package is added without pinning its scope to one registry in `bunfig.toml`, because a name available from two sources is resolved by rules the author did not choose.

**The audit answer is read by where the package runs.** Run `bun audit`, then `bun why <package>` for each name it prints. On 2026-09-30 it reported 36 advisories across six packages, none of them direct, and the first chain `bun why` printed for each was: `undici` through `jsdom`, `sharp` through `miniflare`, `brace-expansion` through `minimatch` under `eslint`, `fast-uri` through `ajv` under `react-doctor`, `esbuild` through `drizzle-kit`, and `js-yaml` through `xmlbuilder2` under `@tanstack/start-plugin-core`. A package reached only through test, lint or build tooling runs on developer machines and the CI runner, not in the Worker; `grep -rlF <package> dist/server` after `bun run build` is a coarse check that it was not bundled, and a hit in a comment is not inclusion, so read the line. An advisory in a package the Worker bundles is right only once it is fixed or recorded with the advisory id, the reason it is not reachable, and a date to look again. The CI step's direct-only rule means a transitive advisory in bundled code never fails a build, so the review is where it gets weighed.

**Nothing watches for new advisories between pull requests.** GitHub lists Dependabot security updates as unsupported for the `bun` ecosystem ([supported ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories)), and the comment in `dependabot.yml` says the same. The only advisory check is the CI audit step, which runs when a pull request or a push to `main` happens and has no schedule. Whether the repository's Dependabot alerts are switched on was not observed.

**The workflow cannot be turned against the repository.** In `ci.yaml`, right is what it holds now: `pull_request` rather than `pull_request_target`, so a fork's code runs with no secrets and a read-only `GITHUB_TOKEN` ([GitHub events docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)); a top-level `contents: read`; every `uses:` pinned to a 40-character SHA. Wrong is a new job that widens `permissions`, a `uses:` on a tag or branch, or a secret passed to a step that also runs code from the pull request. A version comment beside a SHA is not checked by anything, so compare it with the action's release when Dependabot bumps one.

**A secret never entered the history.** `.gitignore` excludes `.env*` except `.env.local.example`, and `.dev.vars*` except `.dev.vars.example`. Run `git log --all --diff-filter=A --name-only` and read every env-like path it lists. On 2026-09-30 the only ones ever added were two example files, holding placeholders. Where a real value appears, deleting the file does not help, because clones and CI caches keep it; the value is revoked at its issuer and replaced, which for the secrets here `docs/DEPLOYMENT.md` describes.

**Topics with no counterpart here.** The book's container base image, its digest and a container scan have none, because the Worker ships as a JavaScript bundle to Cloudflare's runtime and the repository builds no image. A separate SBOM file has none today either: `bun.lock` is the resolved list of what the build installs, and nothing records which of it `dist/server` bundled.

## Reproduce locally

Check that a lock mismatch fails the install without touching the tracked files: in a scratch copy of the repository, change one version in `package.json` and run `bun install --frozen-lockfile --ignore-scripts`. `error: lockfile had changes, but lockfile is frozen`, which is what a changed `clsx` version answered on 2026-09-30, means CI would refuse the same change. A clean install means the version you changed already matched `bun.lock`, which proves nothing, so pick a version the lock does not hold.

Check an advisory's reach with `bun audit`, then `bun why <name>`. A chain that ends at a `dev` entry of `my-app` means the package reaches only tooling. A chain that ends at a runtime dependency means it may be bundled, and `bun run build` followed by a search of `dist/server` for the package's code settles it.

## Fix and pin

Fix a vulnerable direct dependency by raising its exact version in `package.json` and committing the `bun.lock` change with it. For a transitive one, raise the direct dependency that pulls it in first; an entry in `overrides` is the fallback, and it stays pinned by `bun install --frozen-lockfile` like any other version. After either, run `bun run test` and `bun run smoke`, because a dependency update changes behaviour the unit tests may not reach.

What a pull request adds to CI is pinned the same way the existing steps are: a new action by SHA, a new permission named at the job that needs it, and a new tool through `mise.toml` so that its version has one place to change.
