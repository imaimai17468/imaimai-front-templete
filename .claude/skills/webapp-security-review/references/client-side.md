# Client-side security

Draws on chapter 22 (クライアントサイドセキュリティ).

Everything shipped to the browser is under the user's control. The bundle can be read, the DOM and Web Storage edited, and any request the UI can make can be sent without the UI, so a hidden button, a disabled field or a value kept in a script decides nothing. The browser is also a place where input turns into effects without the server seeing it: a value read from the URL, from storage, from another window or from an API answer can reach code that parses HTML, runs script, navigates, or picks where a request goes. A review pairs each such source with the sink it reaches and judges the pair; a source on its own is harmless, and so is a sink fed only literals. The same-origin policy does not help here, because every one of these flows stays inside this origin.

## Where the decision lives here

The client code that reads outside input is small, and that is a property to keep rather than a guarantee.

- **URL input.** No route declares `validateSearch` and no component calls `useSearch`; the only read of a query string is `new URL(request.url).searchParams.get("key")` in `src/routes/api/avatars.ts`, which runs on the server. Nothing reads `location.hash`.
- **Navigation.** `SignInButton` (`src/routes/login/-components/sign-in-button.tsx`) calls `window.location.assign("/")` with a literal, and `UserMenu` calls `window.location.reload()`. Google sign-in passes the literal `callbackURL: "/"` in `startGoogleSignIn` (`src/lib/auth/sign-in/client.ts`); Better Auth's server checks a `callbackURL` against its trusted origins in `originCheckMiddleware`, and its client's redirect plugin (`better-auth/dist/client/fetch-plugins.mjs`) assigns `window.location.href` from the server's answer only after `isSafeUrlScheme` rejects the schemes Better Auth lists as dangerous.
- **Where requests go.** Components call server functions through the RPC stubs the compiler generates, and `createSubmitProfile` (`src/routes/_authed/profile/-components/profile-form/submit-profile.ts`) calls exactly two of them. No component builds a URL for `fetch`.
- **Web Storage.** `git grep -n -e localStorage -e sessionStorage -- src` found nothing. Two libraries use it: `next-themes` writes the `theme` key and reads it back in the inline script it puts at the top of `<body>`, which adds the stored string as a class on `<html>`, a DOM token rather than parsed markup; `ModeToggle` in the header sets the theme to `light` whenever `needsThemeNormalization` in `src/shared/components/header/mode-toggle/theme-cycle.ts` finds a value other than `dark` or `light`. Better Auth's client writes a `better-auth.message` key to tell other tabs about session changes (`broadcast-channel.mjs`). The session itself is an `HttpOnly` cookie, which no script can read.
- **Other channels.** `git grep` found no `postMessage` listener, `WebSocket`, service worker registration, `eval`, `new Function` or `document.cookie` under `src/` on 2026-09-30.
- **Hiding is not authorizing.** The `_authed` guard redirects a signed-out visitor away from `/profile`; `access-control.md` covers why that authorizes nothing.

## Checks

**Every read of the URL is paired with its sink.** Run `git grep -n -e validateSearch -e useSearch -e useParams -e 'location.hash' -e 'location.search' -e searchParams -- src`. For each hit, follow the value to where it is used. Right is a value shown as a JSX child, or one parsed by a schema into a literal set before any use. Wrong is a value reaching an HTML sink (`xss.md`), a navigation, or a request destination. `decodeURIComponent`, `atob` and `JSON.parse` change the encoding of a value and leave it just as untrusted.

**A redirect target read from input is an app path or a known name.** Today there is none. The first one, typically a `redirect` or `next` search param on `/login`, is right where the route maps a name to a route it knows (`{ profile: "/profile" }`) or accepts a path only after checking that it starts with exactly one `/`, contains no backslash and no control character, and still has this origin once parsed with `new URL(value, location.origin)`. Wrong is `startsWith("/")` alone, which passes `//attacker.test` and `/\attacker.test`, which browsers read as another host, or any prefix test on a full URL, which `https://app.example.com.attacker.test` passes. A value passed on as Better Auth's `callbackURL` is also checked by Better Auth's server, which does not excuse the page from checking it before it navigates on its own.

**Client code does not choose where a token-carrying request goes.** Run `git grep -n -e 'fetch(' -e 'method:' -- src/routes src/shared/components`. Right is calls to generated server functions or to fixed paths, with the operation chosen from a table the code defines. Wrong is a path, a server function id or a method read from the URL, storage or a message and then sent, because the browser attaches the session cookie and the CSRF middleware (`csrf.md`) sees a same-origin request and lets it through.

**Stored values are input, not state the app can trust.** For each `localStorage` or `sessionStorage` read that appears, find its writer and its sink. Right is a preference validated on read, as the theme is. Wrong is a role, a user id, a price or a feature flag read from storage and acted on, and wrong is a token placed there, because any script running in this origin can read storage, where it cannot read an `HttpOnly` cookie.

**A cross-window message is checked for its sender and its shape.** The first `addEventListener("message", …)` is right where it compares `event.origin` with one exact origin, checks `event.source` where the sender window is known, and decodes `event.data` with a schema before use; a sender uses an exact target origin, never `"*"`. Wrong is a prefix test on the origin, or a trusted origin used as a reason to skip the schema, since that origin may be forwarding what its own users typed.

**Nothing the server keeps secret reaches the bundle.** Run `bun run build`, then `ls dist/client/assets | grep -c '\.map$'`, which printed `0` on 2026-09-30, and check that every module reading a secret (`src/lib/auth/secret.ts`, `src/lib/auth/better-auth.ts`) imports `@tanstack/react-start/server-only`. Searching `dist/client` for each secret's value is the stronger check; the local values sit in the gitignored env file that an agent's commands are refused from naming, so the user runs that search. A search for the secret's name finds `BETTER_AUTH_SECRET` in the client bundle, because Better Auth ships an environment getter that names the variables it looks up; the name is not a leak and the value is. Right is no value found and no source map published. Wrong is any value in `dist/client`, or an `import.meta.env.VITE_*` variable that holds something other than a public setting, because Vite inlines every `VITE_` variable into client code. The one in use is `VITE_GOOGLE_SIGN_IN`, a switch.

**Untrusted keys do not reach a generic merge.** Run `git grep -n -e 'Object.assign' -e 'merge(' -e '__proto__' -- src`. Right is no generic merge of request, URL or message data, and objects built field by field, as `CurrentUserReader` in `src/shared/gateway/user/read.ts` builds its answer. Wrong is a recursive merge of parsed input into an existing object, which lets a `__proto__` or `constructor` key change every object's prototype.

**A feature that adds a channel brings its own check.** A WebSocket authorizes each message, not only the handshake, and checks the handshake's `Origin`. A service worker does not put session-dependent answers in Cache Storage without clearing them at sign-out.

## Reproduce locally

For a URL source, open the page with a marker in the parameter the code reads and inspect the result in the browser, not in the server's HTML, because a client-side sink never appears in the response. For a redirect parameter, request the page with `//example.com`, `/\example.com`, `https://example.com` and an app path such as `/profile` in turn, and read where the browser ends up in the Network panel. Landing on `/profile` for the last and staying on this origin for the others means the check holds. Arriving at `example.com` for any of the first three is an open redirect. The same page never reading the parameter at all, which is the case on 2026-09-30 because no route reads one, means the step proved nothing.

For storage, sign in, set a stored value to something outside its allowed set in DevTools' Application panel, such as `theme` to `<b>x</b>`, and reload. The value reset to `light` and no new element in the page means it is validated. A behavior change that the value should not grant, such as a control appearing, means storage is being trusted.

## Fix and pin

Keep reads of outside input at the route, decoded by a schema into the narrowest type the page needs, so a component receives a literal union rather than a string. Map redirect targets through a table of route names, send requests only through generated server functions or fixed paths, and keep authority on the server.

Pin a redirect decision as a pure function from the raw parameter to the path it allows, with one row per shape: an app path, a protocol-relative URL, a backslash form, an absolute URL on another host, a `javascript:` URL, and an empty value, each asserted as the whole result in one `toStrictEqual`. Pin a stored-value reader the way `src/shared/components/header/mode-toggle/theme-cycle.test.ts` covers `needsThemeNormalization`, including a value outside the allowed set.
