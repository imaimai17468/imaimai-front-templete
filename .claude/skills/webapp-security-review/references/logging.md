# Logging and monitoring

Draws on chapter 25 (ログと監視).

A log is reviewed from two sides: whether it holds enough to tell afterwards who did what to which object, and whether it holds something that becomes a leak once the log is read by someone other than the user it describes.
## Where the decision lives here

- **`src/lib/report-error.ts`** is the only code under `src/` that writes a log line. `git grep -n -e 'console\.' -e 'Effect\.log' -e 'Console\.' -- src ':!*.test.*'` found only its `Console.error` on 2026-09-30. `reportError(event, cause)` writes one object, `{ event, message, name, stack }`, copied from the cause, and `report-error.test.ts` pins that shape.
- **Its callers are the user gateway's write paths.** `orNone`, `wroteOneRow` and `succeeded` in `src/shared/gateway/user/index.ts` log a `UserPersistenceError`'s cause under the event name their caller passes, in `src/shared/gateway/user/avatar/update.ts` and `src/shared/gateway/user/update.ts`; `git grep -n -e 'orNone(' -e 'succeeded(' -e 'wroteOneRow(' -e 'reportError(' -- src/shared/gateway` lists every event name. `AvatarObjectOrphaned` and `AvatarKeyNotOwned` put an object key, and with it the user id, into `message`.
- **`wrangler.toml`** turns on Workers Logs with `[observability] enabled = true`, and `docs/DEPLOYMENT.md` says where to read them. Cloudflare's documentation says each invocation also writes a log with request and response details, `head_sampling_rate` defaults to 1 (every request), and logs are kept 3 days on Free and 7 on Paid ([Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)). Which request headers an invocation log holds, and whether `Cookie` is redacted, is not stated on that page and was not observed on a deployed Worker.
- **Better Auth writes a `sessions` row per sign-in** with `ip_address` and `user_agent` (`src/lib/drizzle/schema.ts`), filled from the request headers by `createSession` in `node_modules/better-auth/dist/db/internal-adapter.mjs`. It is the only record of who signed in when, and it goes away with the session.

## Checks

**No log line carries a credential or a body.** Read every `reportError` call and every value its `cause` can hold. Right is an event name and a failure that describes the store, not the user's input. It is wrong today for a failed D1 write: Drizzle wraps every failed query in a `DrizzleQueryError` whose message is the SQL text followed by `params:` and the bound values (`node_modules/drizzle-orm/errors.js`), and `stack` repeats the message. For `user.updateName` those values are the new display name, the `updated_at` timestamp and the user id, so a D1 failure on that path writes the name into Workers Logs. The same holds for any later query whose parameters carry an email, a token or a body. Better Auth's own logger is covered in `authentication.md`, which found its one email line on a path only the dev build reaches.

**The URL carries nothing a log must not keep.** An invocation log records the request, so treat every path and query string as logged. The avatar URL's `key` carries the user id, which `access-control.md` treats as an identifier rather than a credential. Google's sign-in returns to `/api/auth/callback/google` with an authorization `code` and a `state` in the query string, which Better Auth exchanges once; whether that entry in Workers Logs is acceptable for 3 to 7 days is a decision nobody has recorded. Wrong is a new route that takes a token, a reset code or personal data in the query, which `browser-headers.md` also covers.

**A decision the gateway makes is visible afterwards.** The book asks for an event each time authorization refuses and each time a high-risk action succeeds. Here none exists: `AvatarReader` answers `AvatarUnauthorized` or `AvatarInvalidKey` and `ProfileWriter` answers `NotAuthenticated` without writing anything, and a successful name or avatar change leaves only `updated_at` behind. A reviewer cannot, from the logs, tell one user probing others' avatar keys from a single mistyped URL. Record it as a gap in detection and never as an authorization bypass, because the gateway still refuses. The policy table from `SKILL.md` step 1 decides which rows deserve an event once an admin role, a deletion or a visibility setting exists.

**An event is a record with fixed fields, never a string built from input.** `reportError` hands `console.error` an object rather than a line of text, so a newline inside a value belongs to that field rather than starting a second record; how Workers Logs indexes such an object was not checked against Cloudflare's documentation. Right is a new field added to `ErrorReportSchema` with a fixed name and a bounded value, such as a reason code chosen from a closed set. Wrong is a template string that interpolates a request value, and a value copied from the request with no length limit, because one request can then fill an entry up to the size limit Cloudflare places on a log, whose value this reference did not confirm.

**Correlation uses an identifier the server issued.** Nothing here reads or sets `X-Request-ID`. Where a request id is added, generate it on the server or take one Cloudflare supplies, and never trust one the client sent without checking its format and length, because a client-chosen id can collide with another request's on purpose. Whether an invocation log carries Cloudflare's own request id that a `console.error` line can be joined on was not checked.

**Logging does not decide an outcome.** Each caller of `orNone`, `wroteOneRow` and `succeeded` returns its failure answer whether or not the log line was written, and `Console.error` cannot fail. Right is keeping it that way: a check that refuses when logging fails, or allows because it did, couples authorization to a sink nobody tests.

**Topics with no counterpart here.** The Worker has no binding to its own logs and no collector, so log storage, rotation, access and retention are the Cloudflare account's settings, the user's to review in the dashboard. The Worker cannot delete or rewrite its past log entries, which answers the book's concern about an attacker erasing a log kept in the application's own database. Alerting on a burst of failures is not configured anywhere in the repository.

## Reproduce locally

Replay a D1 failure through the real Drizzle driver without a database: in a scratch file, build `drizzle` from `drizzle-orm/d1` over a fake binding whose statements reject, run `db.update(users).set({ name: "Probe Person Name", updatedAt: new Date(0) }).where(eq(users.id, "user-123")).returning({ id: users.id })`, which is the query `writeUserRow` sends, and print the caught error's `message`. On 2026-09-30 it printed the SQL and `params: Probe Person Name,0,user-123`, which is the text `reportError` copies into `message` and `stack`. A message without `params:` means Drizzle changed its wrapper and the finding needs rechecking. An import error means the path moved, which proves nothing about the log.

To see what `bun run dev` writes, make the name write fail and change the name on `/profile`: add a trigger to the local D1 with `bunx wrangler d1 execute DB --local --command "CREATE TRIGGER probe_fail BEFORE UPDATE ON users BEGIN SELECT RAISE(ABORT, 'probe'); END;"`, submit the form, read the dev server's terminal, then drop the trigger with the same command and `DROP TRIGGER probe_fail;`. A `user.updateName` record whose message holds the submitted name confirms the finding. An error toast with nothing in the terminal means the failure never reached `reportError`. A save that succeeds means the trigger was not applied to the database the dev server reads.

## Fix and pin

Decide what a log record may hold in `report-error.ts`, where every line is written, rather than at each call site: log the driver's own error (the `cause` Drizzle attaches) or a fixed description in place of a message that carries parameters, and keep the event name as the join key. Pin it with a case in `report-error.test.ts` that passes a `DrizzleQueryError` carrying a parameter and asserts the whole record in one `toStrictEqual`, so a record that still carries the parameter fails.

When the app gains an event for a refusal or a high-risk change, add it at the gateway that decides, with the actor's id, the action, the target's id and the result as fixed fields, and test it as `SKILL.md`'s procedure tests the decision itself: one case per policy row, asserting the answer and the record together.
