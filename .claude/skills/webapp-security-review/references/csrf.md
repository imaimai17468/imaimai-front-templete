# Cross-site request forgery

Draws on chapter 9 (CSRF).

A session cookie tells the server which session a request belongs to, and nothing about which page built the request. A page on another site can make the signed-in user's browser submit a form or send a request to this app, and the browser may attach the cookie. The attacker never learns the cookie and never reads the answer, and the forgery still succeeds wherever the server acts on the request. The same-origin policy restricts reading a cross-origin response, not sending the request, so it does not stop this. Authentication, authorization and CSRF are three separate questions about one request: whose session it is, whether that user may do this to this object, and whether the user's own page sent it. Passing one says nothing about the other two.

## Where the decision lives here

Two libraries each decide for the endpoints they own, and nothing decides for the rest.

- **Server functions** (`createServerFn` in the `*.fn.ts` files, served under `/_serverFn/`). `createStartHandler` in `@tanstack/start-server-core` 1.169.31 (installed with `@tanstack/react-start` 1.168.49) runs a default request middleware built by `createCsrfMiddleware` with the filter `handlerType === "serverFn"`, and uses it only when the app registers no start instance. This repository has no `src/start.ts`, so the default applies. The decision, read from `createCsrfMiddleware.js`: where the request carries `Sec-Fetch-Site`, only `same-origin` passes; otherwise, where it carries `Origin`, only the request URL's own origin passes; otherwise a same-origin `Referer` passes; a request with none of the three is refused. A refusal is `403` with the body `Forbidden`, and the filter applies to GET server functions as well as POST.
- **Better Auth** (`/api/auth/*`, handed over by `src/routes/api/auth.$.ts`). Better Auth 1.7.2's `originCheckMiddleware` (`better-auth/dist/api/middlewares/origin-check.mjs`) runs on every request except GET, HEAD and OPTIONS, and where the request carries a cookie it requires an `Origin` or `Referer` in the trusted set. `src/lib/auth/better-auth.ts` sets neither `baseURL` nor `trustedOrigins`, so the trusted set is the origin Better Auth derives from the request itself while `BETTER_AUTH_URL` is also unset, which the dev log confirms with its "Base URL is not set" warning. That variable would replace the request's origin and `BETTER_AUTH_TRUSTED_ORIGINS` would add to it; whether the deployed Worker sets either was not checked. Its router also accepts only `application/json` bodies, so an HTML form post that carries a body is refused with 415. The e-mail sign-in and sign-up endpoints add `formCsrfMiddleware`, which refuses a cookieless cross-site navigation outright and checks the trusted set for any cookieless request that carries `Sec-Fetch-*`, `Origin` or `Referer`; that is how it refuses a forced login into an attacker's account.
- **The session cookie** is `better-auth.session_token`, observed on `bun run dev` as `HttpOnly; SameSite=Lax; Path=/` with no `Secure`, because `advanced.useSecureCookies` is `!import.meta.env.DEV`. The production arm adds `Secure` and the `__Secure-` name prefix according to Better Auth's cookie code; that was not observed. `Lax` keeps the cookie off a cross-site POST and a cross-site `fetch`, and still sends it on a top-level cross-site GET navigation.

A `server.handlers` route under `src/routes/api/` is outside both. TanStack's filter excludes it, and Better Auth checks only the paths it serves. Today that gap holds nothing to protect: `src/routes/api/avatars.ts` answers GET only and reads.

## Checks

**The default server-function middleware is still the one that runs.** Run `ls src/start.ts`. Right is no such file, or a `createStart` whose `requestMiddleware` includes `createCsrfMiddleware(...)` with a filter that still covers `handlerType === "serverFn"`. Wrong is a start instance whose `requestMiddleware` omits it: `createStartHandler` then uses that list in place of the default, and the console warning it prints about the missing middleware is skipped when `NODE_ENV` is `production`. Also wrong: `allowRequestsWithoutOriginCheck: true`, or a `secFetchSite` option that admits `same-site` or `cross-site`, because a sibling subdomain is same-site and can be a different, less trusted origin.

**Every state-changing API route checks where the request came from.** Run `git grep -n -A6 'handlers:' -- src/routes/api`. Right is GET-only handlers that read, or a handler that delegates to Better Auth. Wrong is a POST, PUT, PATCH or DELETE handler that acts on the session with no check of `Sec-Fetch-Site` or `Origin`, because nothing upstream checks it for that route.

**Nothing changes state on GET.** Run `git grep -n 'method: "GET"' -- src` and read each handler, and read every `GET:` in `src/routes/api/`. Right is a read with no side effect, as `getCurrentUserFn` in `src/shared/gateway/user/read.fn.ts` is. Wrong is a GET that writes, because `SameSite=Lax` sends the cookie on a top-level cross-site link, and on this site an `<img>` in user content or the router's `defaultPreload: "intent"` preload (`src/router.tsx`) sends the request without a click. Moving a write to POST removes that route and adds no origin check of its own.

**Better Auth's checks are not loosened.** Read the object passed to `betterAuth` in `src/lib/auth/better-auth.ts` for `disableCSRFCheck`, `disableOriginCheck`, `trustedOrigins`, `trustedProxyHeaders`, `crossSubDomainCookies` and `defaultCookieAttributes`. Right is none of them, or `trustedOrigins` naming exact origins. Wrong is `disableOriginCheck: true`, which in this version also turns the CSRF check off unless `disableCSRFCheck` is set explicitly, a wildcard origin pattern, `trustedProxyHeaders: true` with no proxy that overwrites `X-Forwarded-Host`, or `sameSite: "none"`.

**`x-tsr-serverFn` is not a defense.** A request to a server function without `x-tsr-serverFn: true` but with `Sec-Fetch-Site: same-origin` still ran `updateProfileFn`'s handler and wrote the name, then answered 500 about the response format. Any check of this class therefore ends with reading the state back; a status alone does not say whether the write happened.

**Client code does not choose where a token-carrying request goes.** A forged request can also be sent by this app's own JavaScript when it builds the destination or the method from a URL or a message. `client-side.md` holds that check.

**A request that passes the origin check is still authorized.** The origin check says the app's own page sent it, which says nothing about whether this user may change this object. The boundary service in the `gateway/` directory decides that, as `access-control.md` describes.

## Reproduce locally

Replay a write that works, then change only its origin headers, and read the state back after each. On `bun run dev`, with `U` set to the URL it prints, create a session with `curl -s -c jar -H "Origin: $U" -H 'Content-Type: application/json' -d '{"email":"csrf@example.com","password":"password-1234","name":"Before"}' $U/api/auth/sign-up/email`. Find `updateProfileFn`'s id with `curl -s $U/src/shared/gateway/user/update.fn.ts | grep -o 'createClientRpc("[^"]*")'`; the id is base64 JSON naming the export, and the one naming `updateProfileFn` is the one to use.

Send the baseline as `curl -s -b jar -H 'x-tsr-serverFn: true' -H 'Sec-Fetch-Site: same-origin' --form-string name=Baseline -w ' %{http_code}\n' $U/_serverFn/<id>`, using `--form-string` because `-F name=<…` makes curl read a file. A 200 and a name of `Baseline` in `curl -s -b jar $U/api/auth/get-session` show the id and the session are live. Then send the same request with `Sec-Fetch-Site: cross-site`, then with no `Sec-Fetch-Site` and `Origin: https://evil.example`, then with neither header, each with a new name. `403 Forbidden` with the name still `Baseline` means the check holds. A 200, or a new name after any status, means a forged request was accepted. A baseline that did not answer 200 or did not change the name means the id or the session was wrong, so the refusals after it proved nothing.

For Better Auth, send `curl -s -b jar -X POST -H 'Origin: https://evil.example' -H 'Content-Type: application/json' -d '{}' $U/api/auth/sign-out`. `403` with `INVALID_ORIGIN` means the check holds, and without the `Origin` header the answer is `403` with `MISSING_OR_NULL_ORIGIN`. A `415` means the body's content type was refused before the origin was looked at, so it says nothing about the origin check.

## Fix and pin

Keep the origin decision in one request middleware rather than in each handler. For server functions that is the default already in place, and a `src/start.ts`, once one is needed, lists `createCsrfMiddleware` in its `requestMiddleware`. A state-changing `server.handlers` route needs the same decision for its path. One way is a `createCsrfMiddleware` in that same list whose filter admits `handlerType === "router"` only for the unsafe methods, because checking a GET page render would refuse every link from another site; that filter is a design not yet tried in this repository. It would also reach `/api/auth/*`, which Better Auth already checks, so either exclude that path or accept that a cross-site POST callback, such as a provider's `form_post`, would be refused. Keep Better Auth's defaults, and add exact origins to `trustedOrigins` only when a second origin must call it.

Nothing pins the 403 today: the rows in `scripts/smoke.ts` are all GET. Pin a new state-changing handler with one test per row: its own page's headers allowed, `Sec-Fetch-Site: cross-site` refused, a foreign `Origin` refused, no origin header refused. For a refused row, assert in one `toStrictEqual` both the status and that the store was not written, such as `{ status: 403, writes: [] }`, so a check placed after the write fails.
