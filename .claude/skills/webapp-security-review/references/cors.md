# Same-origin policy and CORS

Draws on chapter 18 (Same-Origin PolicyとCORS).

An origin is a URL's scheme, host and port together; the path is not part of it, and two hosts of one company are two origins. The browser lets a page send many requests to another origin (links, images, form posts) and stops its script from reading the answer. CORS is how a server tells the browser to let a named origin's script read an answer anyway. It shares a response and does nothing else: it does not say who the user is or whether they may see the data, a non-browser client ignores it entirely, and a preflight that fails prevents no request that can be sent without one, which is why it is no CSRF defense (`csrf.md`). The dangerous configuration is one that lets an origin nobody vetted read an answer the signed-in user's cookie produced.

## Where the decision lives here

Nothing in this repository opts into cross-origin reads. `git grep -n 'Access-Control' -- src` found nothing on 2026-09-30, and neither TanStack Start's server package nor Better Auth writes an `Access-Control-Allow-Origin` header in its installed source. The built Worker, run under `wrangler dev` (which this repository used then), sent no `Access-Control-*` header to any request tried with a foreign `Origin`: `GET /`, `GET /api/auth/get-session`, and preflights to `/api/auth/sign-out` and to a `/_serverFn/` path. The same-origin policy is the whole boundary, and every page and endpoint is readable only by this origin's own scripts.

Two answers to an `OPTIONS` request show that nobody decided preflights either. A preflight to `/api/auth/sign-out` fell through to the router and came back `200` with a rendered document and the document headers, because no handler answers `OPTIONS` there. A preflight to a `/_serverFn/` path came back `403 Forbidden` from the CSRF middleware. Neither grants anything, since both lack `Access-Control-Allow-Origin`.

`bun run dev` behaves differently, and the difference comes from Vite rather than from the app. Vite's default `server.cors` (`defaultAllowedOrigins` in the installed `vite/dist/vite/node/chunks/node.js`) reflects an `Origin` that is `localhost`, a subdomain of `localhost`, `127.0.0.1` or `[::1]` on any port, and `vite.config.ts` does not override it. With `Origin: http://evil.localhost:3000` or `Origin: http://127.0.0.1:9999`, the dev server answered with that origin in `Access-Control-Allow-Origin`, with `Vary: Origin`, and a `204` to the preflight listing every method; with `Origin: https://evil.example` it reflected nothing. It sent no `Access-Control-Allow-Credentials`, so a script on another local origin can read uncredentialed answers from the dev server and cannot read the ones a session cookie produced. A CORS header seen on the dev server says nothing about the Worker.

## Checks

**No response opts into cross-origin reads without a recorded reason.** Run `git grep -n -i 'access-control' -- src` and read `vite.config.ts`, `alchemy.run.ts` and the object passed to `betterAuth` for a `cors` or `trustedOrigins` entry. Right is no hit, as now. Where a second origin genuinely has to read an endpoint, right is that one endpoint listing that one exact origin. Wrong is CORS added to every route to make one caller work.

**An allowed origin is compared whole, never reflected or matched by part.** Read the code that decides `Access-Control-Allow-Origin`. Right is an exact comparison against a list of full origins, scheme and port included, and no header at all otherwise. Wrong is echoing the request's `Origin`, a `startsWith`, `endsWith` or `includes` test (which admits `app.example.com.attacker.test` or `attackerexample.com`), a regex without anchors, or admitting `Origin: null`, which sandboxed frames and `file:` pages send.

**Credentials are shared only with an exact origin, and the answer varies by it.** Right, where a response carries `Access-Control-Allow-Credentials: true`, is a single exact origin in `Access-Control-Allow-Origin` and `Vary: Origin` added to any `Vary` already present, so a cache does not replay one origin's allowance to another. Wrong is reflection combined with credentials, which hands every site the signed-in user's data, or a dynamic origin with no `Vary: Origin`. Browsers refuse `*` together with credentials, so a `*` found on a session-dependent endpoint means that endpoint cannot be read with the cookie, not that it is safe to widen.

**A preflight answers what the endpoint uses, and the real request is checked again.** Right is `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers` naming the methods and headers the caller needs, and the actual request still going through the CSRF check and the `gateway/` boundary (`access-control.md`). Wrong is authentication or authorization done in the `OPTIONS` handler, because a browser may send the preflight without cookies and a script outside a browser skips it. Where `OPTIONS` is reached by accident, as the rendered `200` above is, that answer grants nothing; a handler added for it should answer without a body.

**Same-site is not same-origin.** `SameSite=Lax` on the session cookie (`csrf.md`) compares sites, which ignore the port and cover sibling subdomains, while CORS compares origins. A sibling subdomain that serves user content is same-site: the browser attaches the cookie to its requests, and only the same-origin policy keeps its scripts from reading the answer. Wrong is treating a same-site origin as trusted when adding it to an allow list.

**The dev server's CORS stays a dev-server fact.** Right is judging CORS against the built Worker, as in the reproduction below. Wrong is a fix or a finding based only on what `bun run dev` returns, and wrong is copying the dev server's reflection into Worker code to make a local cross-origin client work.

## Reproduce locally

Change only the `Origin` header on a request that works, then read the `Access-Control-*` headers of the answer. Send `curl -sI -H 'Origin: https://evil.example' <origin>/` and `curl -si -X OPTIONS -H 'Origin: https://evil.example' -H 'Access-Control-Request-Method: POST' <origin>/api/auth/sign-out` against the production build. No command in this repository runs the production build locally since the move to Alchemy, so `<origin>` is a deployed stage's URL, and sending to it is the user's to approve. No `Access-Control-Allow-Origin` in either means no cross-origin read is granted. Seeing `https://evil.example` reflected means any site's script can read that answer, and `Access-Control-Allow-Credentials: true` beside it means it can read the signed-in user's data. An answer that is a `502` or no answer at all means the Worker did not boot, so the step proved nothing. Running the same commands against `bun run dev` shows Vite's reflection for local origins, which tests the dev server rather than the app.

A header only says what the browser was told. To see what a script can read, serve a page from another origin, such as `python3 -m http.server 5174` over a scratch directory holding an HTML file that runs `fetch("<url>/api/auth/get-session", { credentials: "include" })`, open it at `http://127.0.0.1:5174/` while signed in on the dev URL in the same browser, and watch the console and the Network panel. Record three things separately, because each has a different cause: whether the request was sent, whether the session cookie went with it, and whether the script could read the body. `127.0.0.1` is a different site from the dev URL's host, so `SameSite=Lax` keeps the cookie off this request. The request asks for credentials and the answer carries no `Access-Control-Allow-Credentials`, so the browser withholds the body even though Vite reflected the origin, and the console shows a CORS error: that is the expected state. A session readable in the body would mean the cookie was sent and the answer shared, which is a finding. The built Worker cannot be used for this step, because its build disables e-mail sign-in and Google sign-in needs a redirect URI registered with Google for that host.

## Fix and pin

Add CORS per endpoint rather than globally, from a list of exact origins held in one place, with credentials only where the caller needs them and `Vary: Origin` whenever the header depends on the request. Keep the CSRF check and the gateway boundary on the actual request.

Pin the decision as a pure function from the request's `Origin` to the headers it adds, and test one row per case: the allowed origin, a foreign origin, an origin that shares a suffix with the allowed one, `null`, and no `Origin`. Assert each row's whole header set in one `toStrictEqual`, such as `{ "Access-Control-Allow-Origin": allowed, "Access-Control-Allow-Credentials": "true", Vary: "Origin" }` for the allowed row and `{}` for every other. A test run in Node reads every body regardless of CORS, so it shows the headers are right and never that a browser withheld a response; the browser step above covers that.
