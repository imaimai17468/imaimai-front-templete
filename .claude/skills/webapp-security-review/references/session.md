# Session

Draws on chapter 5 (セッションのセキュリティ).

A session carries one sign-in forward to every later request, so whoever holds the cookie is the user until the session ends. The questions are what the cookie holds, which requests the browser sends it on, when the server stops accepting it, and whether a copy taken before sign-out still works.

## Where the decision lives here

The session is a row in the D1 `sessions` table (`src/lib/drizzle/schema.ts`), and the cookie carries that row's random token together with an HMAC of the token under `BETTER_AUTH_SECRET`. On each read, Better Auth's `/get-session` (`node_modules/better-auth/dist/api/routes/session.mjs`) verifies the HMAC, looks the token up in D1, and treats a missing or expired row as signed out. `session.cookieCache` is unset, so no read is answered from the cookie alone.

- `authOptions` in `src/lib/auth/options.ts` sets the cookie's `Secure` flag through `advanced.useSecureCookies: !isDevBuild`, which `src/lib/auth/better-auth.ts` passes as `import.meta.env.DEV`, and the lifetime through `session.expiresIn` (7 days) and `session.updateAge` (1 day).
- `CurrentSession` in `src/lib/auth/session/index.ts` calls `getAuth().api.getSession` with the request's headers, and `pickCaller` in `caller.ts` keeps only `id` and `email`. Every gateway boundary reads the caller through it.
- Sign-out is `endSession` in `src/lib/auth/sign-in/client.ts`, which `src/lib/auth/sign-in/index.ts` re-exports as `signOut` and the header's user menu (`src/shared/components/header/user-menu/user-menu.tsx`) calls before reloading the page. It posts to `/api/auth/sign-out`, which deletes the row and expires the cookies.

## Checks

**The session cookie is Secure, HttpOnly and host-only in production.** The production build answers sign-out with `Set-Cookie: __Secure-better-auth.session_token=; Max-Age=0; Path=/; HttpOnly; Secure; SameSite=Lax`, and `bun run dev` sets `better-auth.session_token` with `Max-Age=604800; Path=/; HttpOnly; SameSite=Lax` and no `Secure`, because it serves plain http. No `Domain` is set, so the cookie goes only to the host that set it. The code is right while `useSecureCookies` stays pinned. It is wrong where that option is removed, because with no `baseURL` Better Auth then decides `Secure` from `NODE_ENV`, which a Worker does not have, and where `advanced.crossSubDomainCookies` or `defaultCookieAttributes` adds a `Domain`. Better Auth applies the `__Secure-` prefix and not `__Host-`, and `__Secure-` requires only `Secure`, so it does not stop a sibling subdomain from setting a cookie of the same name for the parent domain. That matters once the app shares a registrable domain with hosts it does not control.

**Sign-out revokes the copy as well as the browser's cookie.** `/sign-out` deletes the D1 row before it expires the cookies (`sign-out.mjs`), so a cookie copied before sign-out finds no row and `/get-session` answers `null`. `/sign-out` logs a failed delete and still expires the cookies and answers success, so the copy survives a D1 error, and only the replay below shows which happened. The code is wrong where `session.cookieCache` is turned on: the `session_data` cookie then answers a read without the D1 lookup until its own `maxAge` runs out (300 seconds by default), so a copied pair of cookies outlives the sign-out for that long. A custom read that decodes the cookie instead of calling `getSession` reopens the same gap.

**The 7-day lifetime slides, and nothing caps it.** `/get-session` extends `expiresAt` to seven days from now once a day has passed since it was last extended, so the session ends after seven days without a request and never ends while it is used at least once a week. There is no absolute lifetime. Where one is required, `session.disableSessionRefresh: true` makes the 7 days count from sign-in. Where only sensitive actions need a recent sign-in, the freshness check below is the tool. The cookie's own `Max-Age` equals `expiresIn` and bounds only the browser. The server enforces `expiresAt`.

**Signing in always issues a new token.** Both `/sign-in/email` and the Google callback create a new row with a freshly generated token, and a signed-out visitor gets no session cookie at all, so there is no pre-sign-in identifier for an attacker to plant and have upgraded. Signing in while an earlier cookie is still sent returns a different token and leaves the earlier session valid. That is how a second device works rather than a fixation. The code is wrong where a new endpoint or plugin writes a `userId` into an existing session row instead of creating one.

**Ending other sessions is possible, and nothing in the app offers it.** `/revoke-session`, `/revoke-sessions` and `/revoke-other-sessions` exist and read the session from D1 rather than from a cache, and `/list-sessions` requires a session created within the last day (`freshAge`). `git grep -n -e revokeSession -e revokeOtherSessions -e revoke-session -- src` finds no caller of them. Deleting a `users` row removes its sessions through the `onDelete: "cascade"` on `sessions.user_id`, which stops an account as a whole. Where a review requires "sign out everywhere" or a response to a stolen session, the endpoint exists and the page does not.

**The signing secret is the revocation of last resort.** The session cookie is verified with `BETTER_AUTH_SECRET` alone, so replacing that secret makes every existing cookie fail verification and signs every user out at once. A token read from D1 does not produce a cookie that verifies without the secret, and a leaked secret does not produce one without a token that is in D1, so each leak alone falls short of a session. The `/get-session` JSON does carry `session.token` to the page's JavaScript, which is harmless only while nothing accepts a bare token. A plugin that authenticates from a token in a header changes that, so read what it accepts before adding one.

**A sensitive action checks how recent the sign-in is.** Better Auth applies `freshAge` to `/list-sessions` and `/unlink-account`, but a gateway service sees only the `Caller` that `pickCaller` returns, which carries no `createdAt`. A new service that deletes data, exports it in bulk, or changes where the account's mail goes is wrong where it accepts any live session. Extend `Caller` with the session's creation time and compare it with a threshold the policy table states.

**The token stays out of URLs and logs.** The token travels only in the cookie, and `/get-session` answers with `Cache-Control: no-store`. A new route is wrong where it accepts a session token in a query string, or logs a `Cookie` or `Set-Cookie` header, because a URL lands in history, `Referer` and access logs. A cookie-bearing `POST` from a foreign origin is refused with 403 `INVALID_ORIGIN`, which belongs to the CSRF review.

## Reproduce locally

Replay a cookie that exists, because a made-up value answers `null` whether revocation works or not. On `bun run dev`, create a probe account with `POST /api/auth/sign-up/email` (an `Origin` header naming the dev URL, and a JSON body with `email`, `password` and `name`) and copy the `better-auth.session_token` value from its `Set-Cookie`. Send `GET /api/auth/get-session` with that cookie and confirm a session comes back; a `null` here means the copy is wrong, and nothing after it proves anything. Change one character of the value and send it again: `null` means the HMAC check holds, and a session means it does not. Post to `/api/auth/sign-out` with the original cookie and the `Origin` header, then replay `GET /api/auth/get-session` with the same copied value. `null` means the row was deleted and the copy is dead. A session means sign-out left the copy usable, and a 403 `INVALID_ORIGIN` or `MISSING_OR_NULL_ORIGIN` on the sign-out means it never ran, so the replay tested nothing. `GET /profile` with the same cookie answers 200 while the session is live and 307 to `/login` once it is not.

For "sign out everywhere", sign in twice to get two cookies, post to `/api/auth/revoke-other-sessions` with the second, and replay `/get-session` with the first: `null` means the other session ended, and the second cookie should still answer.

## Fix and pin

Keep the lifetime, cookie and cache decisions in `authOptions` in `options.ts`, and name each one there rather than relying on a default, as `useSecureCookies` and `rateLimit.enabled` already are, because Better Auth decides at least those two defaults (the cookie's `Secure` flag while no `baseURL` is set, and whether the rate limiter runs) from `NODE_ENV`, which a Worker does not have.

`src/lib/auth/options.test.ts` builds Better Auth from `authOptions` over the memory adapter and pins the rate limiter only. Extend it to assert in one `toStrictEqual` what `(await auth.$context)` resolves: `sessionConfig`'s `expiresIn` and `updateAge`, the name and attributes of `authCookies.sessionToken` for a production build, and `options.session?.cookieCache`. The sign-out replay above has no automated counterpart, because it needs a Worker with D1. `bun run smoke` boots the built Worker under workerd and is the place a request-level check of it would run.
