# Authentication

Draws on chapter 4 (認証のセキュリティ).

Authentication is every route by which a request comes to be treated as a given user, and a strong sign-in form does not help where a recovery flow, a linking endpoint or an unlimited retry loop reaches the same account more cheaply. Here that set of routes is whatever Better Auth's catch-all serves, so the review lists what that router exposes under the current options, not only the sign-in button.

## Where the decision lives here

`src/lib/auth/better-auth.ts` builds the one Better Auth instance, and `src/routes/api/auth.$.ts` hands every `GET` and `POST` under `/api/auth/` to its `handler`, so each endpoint Better Auth enables is reachable from the internet whether or not a page calls it. The options decide which ones answer:

- `emailAndPassword.enabled` is `import.meta.env.DEV`, so a production build signs in only through Google (`socialProviders.google`). `/api/auth/sign-in/email` answers 400 `EMAIL_PASSWORD_DISABLED` and `/api/auth/sign-up/email` answers 400 `EMAIL_PASSWORD_SIGN_UP_DISABLED` on the built Worker.
- No `rateLimit`, `baseURL`, `trustedOrigins` or `plugins` option is set, so each of those takes Better Auth's default, which the checks below state for the installed 1.7.2.
- `readAuthSecret` in `src/lib/auth/secret.ts` throws when `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID` or `GOOGLE_CLIENT_SECRET` is absent or empty, and `secret.test.ts` pins both answers.

`src/lib/auth/sign-in/` is the browser side: `startGoogleSignIn` in `client.ts` sends `callbackURL: "/"`, and the dev arm in `dev.ts` signs in as `DEV_USER`, whose password sits in the source because `selectSignIn` in `index.ts` folds that arm out of a production build.

## Checks

**Password storage and policy do not apply to a production build.** The book's password topics (a slow salted hash, its cost, a pepper, rehashing, length rules) have no code to check in production, because `emailAndPassword.enabled` is false there and no `credential` row can be created. In dev, Better Auth hashes with its default scrypt into `accounts.password` (`src/lib/drizzle/schema.ts`), with a minimum length of 8 and a maximum of 128. The code is wrong the moment a change turns `enabled` on outside dev: every one of those topics then becomes a check, starting with the minimum length and the absence of any breached-password lookup.

**The rate limiter is off in the deployed Worker.** Better Auth 1.7.2 sets `rateLimit.enabled` to `options.rateLimit?.enabled ?? isProduction` (`node_modules/better-auth/dist/context/create-context.mjs`), and `isProduction` compares `NODE_ENV` read at runtime from `process.env` (`node_modules/@better-auth/core/dist/env/env-impl.mjs`). `NODE_ENV` is not a Worker binding, `dist/server/wrangler.json` carries `"vars":{}`, and the built bundle still reads it at runtime rather than as a literal, so the limiter is disabled, along with its default rule of 3 requests per 10 seconds on `/sign-in`, `/sign-up`, `/change-password` and `/change-email`. The code is right where `better-auth.ts` sets `rateLimit.enabled` explicitly, as it already pins `useSecureCookies` for the same reason, and wrong while the option is absent. Google limits guesses against its own sign-in, so what the missing limiter exposes here is the endpoints this Worker serves itself, such as `/sign-in/social`, which writes a `verifications` row per call.

**Each endpoint the catch-all serves is its own entrance.** Read each gate in `node_modules/better-auth/dist/api/routes/` against the options. Under the current options, `/change-email` refuses because `user.changeEmail.enabled` is unset, `/delete-user` refuses because `user.deleteUser.enabled` is unset, and `/request-password-reset` answers 400 `RESET_PASSWORD_DISABLED` because no `sendResetPassword` is configured. `/update-user` requires a session and refuses an `email` field. `/link-social` requires a session and refuses a provider account whose email differs from the user's unless `accountLinking.allowDifferentEmails` is set, and `/unlink-account` refuses the last account. The code is wrong where a new option or plugin switches on an endpoint (a password reset, an email change, MFA, passkeys) without that endpoint getting its own row in the policy table and its own entry in the rate limiter's rules.

**A failed sign-in says nothing about whether the account exists.** `/sign-in/email` answers 401 `INVALID_EMAIL_OR_PASSWORD` to an unknown email and to a wrong password alike, and on the unknown-email path it hashes the submitted password anyway, which narrows the timing difference without claiming to remove it. `/sign-up/email` does distinguish: an existing email answers 422 `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL` while `requireEmailVerification` is unset and `autoSignIn` is not false (`sign-up.mjs`). Setting `requireEmailVerification` makes an existing email answer like a new one. Both are dev-only here. For the production sign-in, account existence is Google's to hide. The check turns live when email sign-up is enabled for production, where the 422 then lists registered addresses, and where a reset flow is added, whose answer must not change with the email.

**The address a sign-in returns to is checked against the request's own origin.** Better Auth's origin-check middleware (`node_modules/better-auth/dist/api/middlewares/origin-check.mjs`) refuses a `callbackURL`, `errorCallbackURL` or `newUserCallbackURL` that is neither a relative path nor a trusted origin, and with no `trustedOrigins` option and no `BETTER_AUTH_TRUSTED_ORIGINS` binding, the only trusted origin is the one the request arrived on. Better Auth reads that name, and `BETTER_AUTH_URL`, from `process.env`, which a Worker fills from its bindings, so a var or secret by either name widens the set with no code change. `wrangler.toml` defines neither today. The code is right while the client passes relative paths as `startGoogleSignIn` does. It is wrong where `trustedOrigins` gains a wildcard, or where a page reads a return address from its own query string and navigates to it after sign-in without the same check, because that navigation never passes through Better Auth.

**The base URL comes from the request.** With no `baseURL` and no `BETTER_AUTH_URL`, the handler in `node_modules/better-auth/dist/auth/base.mjs` derives the base URL from each request's URL, and Better Auth builds the OAuth `redirect_uri` and any emailed link (a reset or verification URL) from it. Google compares `redirect_uri` with the URIs registered for the client, which bounds the OAuth case. An emailed link has no such second check, so set `baseURL` from configuration before adding any flow that sends one. Whether Cloudflare can deliver a request to this Worker under a hostname nobody routed to it was not verified here, so treat the request's host as client-supplied.

**No log line carries a credential.** `git grep -n -e 'console\.' -- src ':!*.test.*'` finds nothing under `src/` today. Better Auth's own logger writes the submitted email at info level when a sign-up hits an existing address (`sign-up.mjs`), which only the dev arm reaches. A new log line on an auth path is wrong where it prints a `Cookie` or `Set-Cookie` header, a request body of `/api/auth/*`, or a token, and an email is personal data that needs a stated reason and retention before it is logged.

**MFA and passkeys are not configured.** `plugins` is unset, so no second factor exists to review. When one is added, its enrolment, removal and recovery endpoints are entrances in their own right and need the same re-authentication a password change would.

## Reproduce locally

Check the rate limiter against the production build, because `bun run dev` runs a different arm of `emailAndPassword`. Run `bun run build`, start the built Worker with `bunx wrangler dev -c dist/server/wrangler.json --port 8788` passing `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` with `--var` as `scripts/smoke.entry.ts` does, and send six `POST http://localhost:8788/api/auth/sign-in/email` with a JSON body inside ten seconds. A 429 from the fourth request on means the limiter is on. Six answers of 400 `EMAIL_PASSWORD_DISABLED` mean every request reached the handler and the limiter let them all through, which is what the build answered on 2026-09-30. Requests spread over more than ten seconds prove nothing, because each window starts fresh. A 500 from `/sign-in/social` there means the throwaway D1 has no tables, not a result about the limiter.

Check enumeration and the return address on `bun run dev`, against the URL it prints, with an account you create yourself. Sign up a probe account with `POST /api/auth/sign-up/email`, then send `POST /api/auth/sign-in/email` once with an email nothing registered and once with the probe's email and a wrong password, with an `Origin` header naming the dev URL. Two identical 401 `INVALID_EMAIL_OR_PASSWORD` bodies mean the answer does not enumerate. Different bodies or statuses mean it does, and a 403 `INVALID_ORIGIN` means the `Origin` header named another origin, so nothing was compared. Then send `POST /api/auth/sign-in/social` with `{"provider":"google","callbackURL":"https://evil.example/"}`: a 403 `INVALID_CALLBACK_URL` means the check holds, and a 200 carrying a Google `url` means an external return address was accepted.

## Fix and pin

Set `rateLimit` explicitly in `better-auth.ts` with `enabled: true` and a store that outlives an isolate. The default `memory` store is a module-level `Map`, so it counts only the requests one isolate happens to see. `storage: "database"` needs a `rateLimit` model with `key`, `count` and `lastRequest` added to `src/lib/drizzle/schema.ts` and a migration. Better Auth reads the client IP from `x-forwarded-for` by default and falls back to one bucket shared by every client when that header does not resolve, so point `advanced.ipAddress.ipAddressHeaders` at the header Cloudflare sets for the client address after confirming its name in Cloudflare's documentation.

No test builds the Better Auth instance today, because `buildAuth` reads its secrets from the Cloudflare environment. Pin these options by making them a function of the secrets and the build flag, so a test can pass `betterAuth` the result and assert the resolved context in one object: `(await auth.$context).rateLimit`'s `enabled` and `storage`, next to the `emailAndPassword.enabled` value for each build. Each endpoint switched on later gets a test of its policy rows, the allowed answer as well as the refused one, as `SKILL.md`'s procedure says.
