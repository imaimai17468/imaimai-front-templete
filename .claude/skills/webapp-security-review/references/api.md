# API

Draws on chapter 19 (APIのセキュリティ).

An API endpoint is an HTTP request and response like a page, and a caller can send it without the page: change an id, add a field the form never sends, switch the method or the content type, or send it a thousand times. Each endpoint is therefore a public contract of its own, and a review reads four things off it: who may reach which object, which fields may arrive and which may leave, how much work one caller can cause, and which endpoints exist at all.

## Where the decision lives here

The API surface is two kinds of entrance, listed by `git grep -n -e 'createServerFn(' -e 'handlers:' -- src`:

- A `createServerFn` in a `*.fn.ts`, which the framework serves under `/_serverFn/<id>` and the page calls through a generated stub. `getCurrentUserFn` in `src/shared/gateway/user/read.fn.ts` is a GET, and `updateProfileFn` and `uploadAvatarFn` in `src/shared/gateway/user/update.fn.ts` are POSTs.
- A `server.handlers` entry in a file route under `src/routes/api/`. `src/routes/api/avatars.ts` serves avatar bytes on GET, and `src/routes/api/auth.$.ts` hands every GET and POST under `/api/auth/` to Better Auth, whose endpoints `authentication.md` lists.

What may arrive is decided by each server function's validator (`input-validation.md`), which object a caller reaches by the boundary service in the `gateway/` directory (`access-control.md`), and what leaves by the schema the gateway encodes its answer with, such as `UserWithEmailSchema` in `src/shared/entities/user/index.ts`.

## Checks

**Every endpoint is reviewed as if no page called it.** A button the UI hides and a field it makes read-only restrict nothing, because the server function's URL and body shape are visible in the Network panel. For each entrance, read the validator and the boundary service it reaches. Right is a decision made there on the request alone. Wrong is an endpoint whose safety depends on the page never sending a value, such as a handler that trusts a hidden field.

**Object authorization is the boundary's, and an unguessable id is not authorization.** `access-control.md` holds the checks and the reproduction for swapping an id or a caller. The avatar key carries a UUID (`AvatarKeyIds` in `src/shared/gateway/user/avatar/index.ts`), and `AvatarReader` still compares its owner segment with the caller before it reads the bucket, which is the shape a new id-taking endpoint copies. Wrong is an endpoint that reads by an id from the request and relies on the id being hard to guess.

**The answer is built field by field from a schema that names the audience.** `CurrentUserReader` in `src/shared/gateway/user/read.ts` builds its answer from named fields of the decoded row and encodes it with `UserWithEmailSchema`, so a column added to `users` in `src/lib/drizzle/schema.ts` does not leave the Worker until someone adds it there. That answer is for the owner alone: it carries `email`, which `UserMenu` and the profile page show. Right is one output schema per audience (the owner, another user, an operator), each listing its fields. Wrong is a row spread into the answer (`{ ...row }`), or the owner's schema reused for a listing or a public profile, because `email` then reaches every reader of that listing. The first endpoint that shows one user's data to another gets its own schema without `email`, derived from `UserSchema` rather than widened from `UserWithEmailSchema`.

**The fields a request may set are an allow-list, and the server fills in what it knows.** `input-validation.md` holds both layers of the allow-list, the validator's schema and the columns `UserRowUpdate` admits. Beyond them, a value the server already knows never arrives from the client: `ProfileWriter` takes the user id from the session and `updatedAt` from `DateTime.now`, and `AvatarWriter` builds the object key and derives the extension from the MIME type. Right is a new write whose request carries only what the user chooses. Wrong is an owner id, a role, a status or a price read from the body, because a hand-built request sets it to anything.

**Each endpoint accepts one method and states which content types reach its parser.** A server function refuses any other method before parsing, and which bodies each method takes is `data-processing.md`'s; a `PUT` to `updateProfileFn` answered `405` `expected POST method. Got PUT` on 2026-09-30. A file route runs its handler only for a method `handlers` names, or for `ANY`, with HEAD falling back to GET (`node_modules/@tanstack/start-server-core/dist/esm/createStartHandler.js`). Any other method falls through to the router, so a `PUT` to `/api/avatars` answered 200 with the rendered HTML page on 2026-09-30, root loader included. Right is a read on GET with no side effect, as `csrf.md` checks, a write on POST, and a file route that treats the rendered fallthrough as the answer to every method it does not name. Wrong is a state change on GET, which a link preview or a prefetch can trigger.

**The result union is the error contract, and the HTTP status is not.** `updateProfileFn` and `uploadAvatarFn` answer each expected failure as an arm of `UpdateProfileResult` or `UploadAvatarResult` (`src/shared/gateway/user/update.ts`), with a fixed message per arm. A failure that escapes the handler, such as a validator's rejection, rides the same 200 response in its `error` slot, as `input-validation.md` observed. A client, a monitor or a test therefore reads `status` and the `error` slot rather than the HTTP code. Right is a new expected failure added as an arm with a fixed message. Wrong is an expected failure left to throw, because its message is then whatever the throwing code wrote, which `information-leakage.md` checks. `/api/avatars` does use HTTP statuses (400, 401, 404), so the two kinds of entrance follow different contracts, and a new route states which one it follows.

**One caller's work is bounded per request and per time window.** Per request, `MAX_AVATAR_BYTES` bounds a stored avatar and `UpdateUserSchema` bounds a name, and no endpoint lists rows, so there is no page size to cap yet. Per time window, nothing is bounded: no server function has a rate limit, and Better Auth's own limiter is off in the deployed Worker (`authentication.md`). Each `uploadAvatarFn` call runs an R2 put, and a delete of the previous object where there is one, so a signed-in caller can repeat it as fast as the Worker answers. Right, for the first listing, is a server-side maximum on the page size that a larger request cannot raise. Right, for a write that costs money or storage, is a limit keyed by the user id rather than by IP address alone, since one address can hold many users and one user many addresses. Which Cloudflare mechanism supplies such a limit was not looked up for this reference. Wrong is a limit enforced only by the form's `disabled={isPending}`, which a second tab skips.

**The endpoint inventory is the grep, and nothing older runs beside it.** The five entrances above are the whole surface on main, plus the endpoints the Better Auth catch-all serves. There is no versioned prefix and no second deployment of older code. Right is a removed feature taking its `createServerFn` or its route file with it, which also deletes the URL. Wrong is a replacement added under a new name while the old function stays exported and reachable, or a debug route kept behind a path nobody links, since anyone who guesses or learns the path reaches it.

**A value from another service is input.** The `image` column holds whatever Google supplied at sign-up, and `CurrentUserReader` lets it leave only through `httpsUrl` (`src/lib/https-url.ts`), which accepts an absolute `https` URL alone. A future call to an outside API is right where its answer is decoded with a `Schema` at the boundary, bounded in size and time, and mapped into this app's own output schema before it is returned. Wrong is an outside answer relayed whole, which forwards whatever fields that service adds.

**A token never travels in a URL.** Sessions ride the cookie (`session.md`). A future API key or bearer token for a non-browser client is right in the `Authorization` header and wrong in a query parameter, where the Worker's logs, the browser history and a `Referer` keep it.

## Reproduce locally

Change one element of a request that works, and compare both the body and the row. Run `bun run db:push:local`, start `PORTLESS=0 bun run dev` (it serves `http://localhost:5173`), sign in on `/login`, and copy from the Network panel the request the profile page's Save button sends to `/_serverFn/...`. Replay it with `curl`, keeping the session cookie and the `x-tsr-serverFn: true` and `Sec-Fetch-Site: same-origin` headers, and change one thing per send: the method to `PUT`, then the cookie removed. The undeclared-field send is `data-processing.md`'s. Read the row with `bunx wrangler d1 execute DB --local --command "select id, name, email from users"` after each.

A 405 naming `POST` means the method is fixed. `Not authenticated` with the row unchanged is the refusal expected without a cookie. A plain-text 403 `Forbidden` means the request lacked `Sec-Fetch-Site` and the CSRF middleware (`csrf.md`) refused it before the handler ran, so it proves nothing about the endpoint.

## Fix and pin

Put each decision where it binds every caller: the input allow-list in the validator, the object and the caller in the gateway boundary, and the output fields in a schema per audience. Where a new endpoint needs a limit, enforce it in the gateway, before the store is touched.

Pin the output shape by asserting the whole answer in one `toStrictEqual`, as the repository's Testing rule already requires. That assertion lists every key, so a field added by accident fails it without anyone predicting its name, which a test of the form "no `email` key" does not do. Pin the input side with a validator test that sends an undeclared field and asserts the decoded value holds only the declared ones. `src/shared/gateway/user/update.fn.test.ts` tests `parseProfileUpdate` for non-`FormData` input and for valid and invalid names, and has no such row today.
