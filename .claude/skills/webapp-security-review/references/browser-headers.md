# Response headers and browser security

Draws on chapter 17 (HTTPヘッダーとブラウザセキュリティ).

A response header is an instruction to the browser: which scripts it may run, who may frame the page, how much of the URL it sends onward, whether it may guess a file's type, whether it may store the answer. The server only states the policy and the browser enforces it, so a header fixes nothing in the code that produced the response. A missing `Content-Security-Policy` is not an XSS, and a present one does not show the page is free of XSS. `curl` and other non-browser clients ignore all of it. A review therefore asks two things of each header: which response carries it, and what the browser does differently because of it.

## Where the decision lives here

- **Rendered documents** take their headers from `headers: () => DOCUMENT_HEADERS` on the root route (`src/routes/__root.tsx`), and the record itself is `DOCUMENT_HEADERS` in `src/lib/response-headers.ts`. On 2026-09-30, `/` and an unknown path's 404 document carried the same six under `bun run dev` and under the built Worker run by `wrangler dev`: `Cache-Control: private, no-store`, `Content-Security-Policy: frame-ancestors 'none'`, `Cross-Origin-Opener-Policy: same-origin`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`, and `X-Frame-Options: DENY`.
- **Responses a handler builds itself** set their own. `src/routes/api/avatars.ts` adds `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'` and `Cache-Control: private, max-age=31536000, immutable` to an image it serves. Its error answers go through `jsonError`, and the 401 observed carried `Content-Type: application/json` and nothing else.
- **Redirects** carry none. The `_authed` guard's `307` to `/login` for `/profile` answered with `Location` alone, in dev and in the built Worker, which the doc comment on `DOCUMENT_HEADERS` also states.
- **Files under `public/`** are served without passing the root route: the built Worker answered `/favicon.svg` with `Cache-Control: public, max-age=0, must-revalidate` and an `ETag`, and none of the six.
- **No other code in this repository sets a security header.** `src/ssr.tsx` hands every request to `createStartHandler` unchanged, `wrangler.toml` holds no header rules, and `public/` holds no `_headers` file. The Cloudflare zone in front of a deployed Worker can add or overwrite headers, and `DOCUMENT_HEADERS`' doc comment leaves `Strict-Transport-Security` to the zone; what the deployed zone sends was not observed.

`bun run dev` also adds `Vary: Origin` to every answer, which the built Worker does not; `cors.md` covers where that comes from. Judge headers against the built Worker, not the dev server.

## Checks

**Every document carries the record.** Run `curl -sI` against `/`, `/login` and a path no route matches. Right is the six headers above on each. Wrong is a document whose value differs from the record, which happens where a child route's `headers()` sets a name the root sets, because route headers merge name by name and the deepest match wins. Also wrong is a document missing one, which happens where a response is built outside the root route. Run `git grep -n 'headers:' -- src/routes` and read each result; a route that needs a different value, such as a looser `Cache-Control` on a public page, says why in its own `headers()`.

**A response a handler builds carries what its content needs.** For each `new Response` or `Response.json` in `src/routes/api/`, read the headers it sets. Right, for bytes a user uploaded, is a `Content-Type` from the upload allow list plus `nosniff` and a `default-src 'none'` policy, as the avatar answer has, so the browser neither guesses a script out of the bytes nor runs one inside them. `nosniff` does not correct a wrong `Content-Type`, so the type is checked at upload as well (`src/lib/storage/avatar-validation.ts`). Wrong is user bytes served with a type taken from the request, or with no `nosniff`. A fixed JSON error body is lower risk; record whether its headers were a choice.

**The CSP says what it does today, and nothing is added to it to silence an error.** Read the `Content-Security-Policy` value in `src/lib/response-headers.ts`. Today it holds `frame-ancestors 'none'` only, so it restricts framing and does not restrict scripts, and output escaping is the only defense against XSS (`xss.md`). A `script-src` added later has to allow the inline scripts every document already holds: the theme script `next-themes` writes into `<body>`, and the `$R` and `$_TSR` scripts that stream the dehydrated router state. `'self'` alone blocks those, so the policy needs a nonce or hashes; whether this TanStack Start version can put a nonce on its own scripts was not checked. Wrong is `'unsafe-inline'`, `'unsafe-eval'` or `*` in `script-src`, each of which removes most of what the directive adds. Introduce a new policy as `Content-Security-Policy-Report-Only` first and read the violations before enforcing it.

**Framing is refused, and a future embed names its parent.** Right is `frame-ancestors 'none'` in the CSP with `X-Frame-Options: DENY` for older browsers, as now. `frame-ancestors` controls who may frame this app; `frame-src` controls what this app may frame, and swapping them leaves clickjacking open. Wrong, once a page must be embedded, is deleting both headers rather than listing the one parent origin in `frame-ancestors`.

**The URL carries no secret, and the referrer policy is a second line.** `strict-origin-when-cross-origin` sends another origin only the scheme and host, and nothing on a downgrade to http. Read every URL the app builds with data in it. The avatar URL carries an object key, which `access-control.md` covers as an id rather than a credential. Wrong is a token, a reset code or personal data in a path or query, which the browser history and the server logs keep whatever the policy says.

**Session-dependent answers are not stored by shared caches.** Right is `private` on everything a session decides, as the document and the avatar answer have, and `no-store` on documents, which carry the user's name and e-mail in the dehydrated cache. `no-cache` still allows storing and only forces revalidation. Wrong is `public`, `s-maxage` or no `Cache-Control` on a response whose body depends on the cookie.

**`Cross-Origin-Opener-Policy: same-origin` fits the sign-in flow.** It cuts the link between this page and a window it opens on another origin. Google sign-in here navigates the whole page, as the comment on `socialSignInOutcome` in `src/lib/auth/sign-in/outcome.ts` describes, so no popup relies on that link. A move to a popup-based sign-in revisits this header.

**What is absent is absent on purpose.** `Strict-Transport-Security` is left to the zone, as the doc comment on `DOCUMENT_HEADERS` says, which is right only if the zone sends it; confirm with `curl -sI` against the deployed host, which is the user's to run. `Permissions-Policy` is not sent, and nothing in the repository records whether that was decided; the app uses no camera, microphone or geolocation. `X-XSS-Protection` is obsolete and adds nothing.

## Reproduce locally

Read the headers the built Worker sends, because the dev server adds its own. Run `bun run build`, then `bunx wrangler dev -c dist/server/wrangler.json --port 8799` with the three `--var` placeholders `scripts/smoke.entry.ts` passes, then `curl -sI http://127.0.0.1:8799/`, the same for `/nope`, `/profile` and `/api/avatars`. The six headers on `/` and `/nope` mean the record reaches documents. Their absence on a document means a route's `headers()` or a new wrapper around `createStartHandler` changed them. Their absence on the `307` and on the `401` is the current state described above, not a regression. A `502` or a connection error means the Worker did not boot, and says nothing about headers.

To see the browser enforce framing, save a local HTML file with one `<iframe>` whose `src` is the dev URL and open it. An empty frame and a console message naming `frame-ancestors` mean the header is enforced. A rendered app inside the frame means it is not. A frame that fails because the dev server was not running proves nothing, so load the URL on its own first.

## Fix and pin

Change a document header in `DOCUMENT_HEADERS` and nowhere else, and give a handler-built response its headers where it builds the response. Pin both: `scripts/smoke.ts` repeats the record as `EXPECTED_DOCUMENT_HEADERS` and `bun run smoke` checks it on `/`, `/login` and `/auth/auth-code-error` against the built Worker, so a header added to one record fails until it is added to the other. `src/routes/api/-avatars.test.ts` asserts the avatar answer's `Cache-Control`, `Content-Security-Policy`, `Content-Type` and `nosniff` in one `toStrictEqual`, which is the form a new handler's test takes. A header test shows the browser was told; the iframe step above, or an end-to-end browser test, is what shows the browser obeyed.
